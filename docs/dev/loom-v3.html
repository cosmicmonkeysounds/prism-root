Loom v3 design

Loom looks like a screenplay. It is not one. Underneath the capitalised speakers and indented dialogue is a non-linear narrative scripting language with reactive bindings, character simulation (Simulacra), stat systems (Meridian), live-theatre participants, improv coroutines, and a tiered scheduler. v3 keeps the screenplay skin — because writers, stage managers, and directors can read it cold — and brings the engine fully back from v2, organised under one bracket discipline.

The four claims.
  1. Screenplay on the outside. Position, capitalisation, and indentation carry meaning. Quotes, apostrophes, and most punctuation belong to the writer. A .loom file printed and handed to a director is directable.
  2. Narrative VM on the inside. The same file is a program — reactive let, hooks that fire on ledger events, character goals as small state machines, generators that drive ambient life, scenes that coordinate multi-step coroutines, factions that hold collective state. Simulacra and Meridian are folded in as first-class declaration kinds, not bolted on.
  3. Traits compose behavior, not just properties. A TRAIT packages property defaults and hooks, generators, goals, and scenes — anything a CHARACTER can hold. is X, Y mixes them in, defaults flow through, anything declared on the child overrides by name. The "I wrote five similar guards" problem stops at the first guard.
  4. Directives are Luau functions. <sfx: bell> is a call to a function sfx. The core registry ships the audio / lighting / state / control-flow verbs out of the box; a studio adds its own by writing a Luau function and registering it. Loom doesn't grow new keywords — Luau grows new verbs.
  5. A project is a folder of .loom files, rooted at main.loom. Beats live wherever they're easiest to write, characters live in their own files, and diverts cross files at will. The runtime resolves names across the whole project, the way Obsidian resolves wiki-links across a vault.

1. Lineage — the formats v3 descends from

Every choice below is borrowed. Knowing which is which is the cheat sheet for the rest of the document.

TraditionWhat v3 takes
Hollywood screenplay (~1920s) Position-is-syntax: ALL CAPS speaker cues, indented dialogue, parenthetical directions in (parens), action lines flush left, scene headings INT./EXT.
Stage prompt book (Samuel French, BBC radio) The parallel cue column. Production metadata sits next to text, not inside it. v3's triple-backtick fence is that column.
Fountain (Maschwitz/August, 2012) Plain-text screenplay with inference and escape. Defaults are positional; sigils only appear when the writer needs to override the inference.
Ink (inkle, 2016 — 80 Days, Heaven's Vault) Knots (==), once-only choices (*), sticky choices (+), diverts (->), gathers (-), tunnels (-> (…) ->), the […] choice-suppress trick, and the mental model of a playhead.
Twine (Klimas, 2009) A passage is both a file unit and a graph node. A beat in v3 lives wherever the writer puts it — its own file, a folder of siblings, or jammed into main.loom.
Obsidian / Logseq (local-first plain-text notes) Identity by filename. Emergent backlinks from bare capitalised names. Inline key: value properties. No YAML frontmatter required.
SolidJS / Reaktiv / S.js (fine-grained reactivity) Reactive let as a live memo. Predicates re-evaluate when their dependencies change, not on a tick. The model behind hooks, goal predicates, and condition-gated dialogue.

v3 contributes one new thing on the surface: the five-bracket discipline (§5). Underneath, it contributes the integration — Simulacra, Meridian, the weave, the live layer, the prompt book, and the multi-file project all share one parser and one ledger.

2. Loom as a format, not a syntax

A syntax requires you to think in tokens, delimiters, escapes. A format is something a human reads and understands without parsing. Markdown is a format. Fountain is a format. v3 is a format with one extra promise: the same file is the writer's screenplay, the stage manager's prompt book, the producer's breakdown, the simulationist's character sheet, and the runtime's program.

Concretely:

  1. Quotes belong to the writer. ", ', «, " never appear in the grammar. A writer can paste any dialogue verbatim and it parses.
  2. Position over delimiters where position works. A name on its own line is a speaker. An indented line under it is dialogue. A paragraph flush-left is action. A line starting with * or + is a choice. These are positional — exactly as screenplay has done for a century.
  3. Brackets, when used, mean one thing each. Five shapes, five distinct jobs, no overlap. §5.
  4. Printable on paper. Anything the runtime alone cares about lives in a ``` … ``` fence so a producer can mark it as "ignore at the table read."
The skin is not the engine. Loom looks like a screenplay because writers, actors, and directors can read screenplays. But underneath, every .loom file compiles to a node in a reactive graph, a small set of state machines, and a weave of coroutines. The screenplay is a delivery format for a non-linear narrative VM — not a description of it.

3. A Loom project — folders, files, main.loom

A project is a folder. Anywhere in that folder, a file ending in .loom is part of the project. The runtime loads them all, resolves names across them, and starts at main.loom's entry beat.

my-show/ ├── main.loom ← the entry point ├── cast/ │ ├── Wren.loom ← one character per file (optional) │ ├── Player.loom │ └── Bellkeeper.loom ├── locations/ │ ├── Lighthouse.loom │ └── Harbor.loom ├── stats/ │ └── combat.loom ← Meridian: shared stats profile ├── factions/ │ └── KeepersGuild.loom ├── beats/ │ ├── opening.loom │ ├── ringing.loom ← a single beat, on its own │ └── act_two/ │ ├── confrontation.loom │ └── revelation.loom └── generators/ └── HarborChorus.loom ← ambient life

The discipline:

  • main.loom is the entry. Its entry: property names the first beat to play. If entry: is absent, the first == in main.loom wins.
  • The folder tree is for humans, not the resolver. Names are flat across the project; Obsidian/Twine convention. A beat in beats/act_two/revelation.loom is addressable as revelation, or — when disambiguation is needed — as act_two/revelation.
  • Any declaration may live in any file. A character can sit in cast/Wren.loom, or be declared inline at the top of main.loom. The resolver doesn't care; the writer optimises for legibility.
  • Beats can divert into other files. A divert is a -> followed by a beat name. The beat may live anywhere in the project. See §7.
  • Each file declares its own header. tags: are file-scoped; everything else is project-wide.

4. The imperative weave

Loom is imperative on the outside, reactive on the inside. A beat reads top-to-bottom; the playhead advances through prose, dialogue, cues; branches fork at choices and diverts. Around the playhead, a reactive graph holds derived state (let), predicates (goals, hooks), and live collections (factions, cohorts). When a mutation invalidates a predicate, the affected hooks queue — they do not preempt the playhead. The next time the playhead yields (end of line, end of beat, choice prompt, wait), the scheduler drains the queue.

This is the same execution model as Ink with Solid grafted on. The weave is the branching graph traced by all possible playheads through the document; the reactive graph is the dependency graph among lets, predicates, and stats.

The angle-bracket / backtick-fence split is the load-bearing distinction. Does the runtime do something with it? <sfx: bell> fires a Luau function at the booth. ```warn lx14``` is a note for the stage manager four lines ahead of the cue. An author note about pacing is purely fenced.

The triple-backtick fence is borrowed from Markdown for a reason: every writer who has used GitHub, Discord, Notion, or Obsidian already knows what a backtick fence does — it's an out-of-band region. Inline (```warn lx14``` on one line) and block forms both work: 

```note
This scene felt long at the table read. Try cutting the lantern beat;
the silence after the bell carries better than the dialogue.
```

6. The shape of a .loom file

Three zones, mixed freely:

  • Header — a Markdown-style # Title plus key: value properties.
  • Declarations — ROLE (a.k.a. CHARACTER), PERSON, ROSTER, ITEM, LOCATION, FACTION, STATS, TREE, GENERATOR, SCENE, COHORT, TRAIT, plus top-level let bindings. Every declaration is a class (§9.6) — properties, init, method, self.
  • Beats — == knot_name followed by a contract (cast:, setting:) and a woven body.

Scene headings (Fountain-style INT. LOCATION - TIME) sit anywhere in a beat body. They tell a director and a reader where they are; they do not define structure — == does that.

6.1 Comments — // and /* … */

Loom borrows C-style comments — the one piece of authoring grammar that is for the author alone, never the performer, the reader, the runtime, or the production team. A comment is invisible to every audience. It is the "scribbled in the margin in pencil" channel.

  • Line comments — // followed by any text, to the end of the line. The // must be at the start of the line or preceded by whitespace, so URLs in dialogue (https://example.com) stay verbatim.
  • Block comments — /* … */ may span any number of lines. Same whitespace rule on the opener. An unterminated /* is a hard error (L1007UnterminatedBlockComment) — the parser will not silently eat the rest of the file.
// rough order: bell, beat, lantern up, line
WREN
  (quietly)
  It hasn't rung in three days. // pickup pace if Wren's actor is fast

/*
  blocking sketch from rehearsal 04-12:
  Wren is upstage left at the rope. Player enters from SR on the bell.
  Strike: lantern down on "rang".
*/

== ringing
  -> bell_arc

Comments are not recognised inside a ``` … ``` production-metadata fence: the fence is its own out-of-band region and a stage manager's note may legitimately contain // or /* as prose. Use the fence for anything you want a production team to read; use a comment for anything you want only the next author to read.

7. Diverts across files

A divert is -> followed by a beat reference.

FormMeaning
-> ringing jump to beat ringing, found anywhere in the project
-> Lighthouse/ringing jump to beat ringing, disambiguated by folder path (when two beats share a name)
-> Wren jump to the entry beat of the file declaring Wren (typically a character file with a single beat)
-> ask_about with topic: bell, NPC: Wren parameterised divert — fills slots at the call site
-> (ask_about with topic: bell) -> tunnel call: push continuation, jump, resume on <-
<- return from the current tunnel
-> END terminate the playhead

Cross-file diverts are the heart of the multi-file model. A conversation in main.loom can divert into beats/Lighthouse/ringing.loom mid-line; the playhead doesn't notice the file boundary. Diverts at any indentation level work the same way — inside choices, inside <if:> arms, inside <match:> arms, even inside an indented dialogue block as the line that ends the speaker's turn.

Diverts at any time, from anywhere. A character's dialogue can end with a divert that hands the playhead to a beat in another file. A hook fired by a stat threshold can divert into a reaction beat. A generator can yield a divert. The playhead is a cursor over the whole project, not over one file. 
WREN
  The bell hasn't rung in three days.
  -> Lighthouse/ringing             ← divert ends Wren's turn

* Tell me about the keepers.
  -> cast/Wren#backstory            ← cross-file with explicit knot

* Maybe later.
  -> END

The # form addresses a specific knot inside a target file (used when a file has more than one beat and the divert needs to pick). When omitted, the file's entry beat is the target.

8. Typed slots — the one generic mechanism

Generics in narrative happen at every scale. A merchant beat works for any merchant. A guard character template instantiates any guard. A recognition scene needs a mentor and a mentee. All of these are the same shape: a typed slot, filled at the call site. 

CHARACTER Keeper                       ← abstract: voice has no default
  voice: any
  home:  any of LOCATION
  reputation: 0 to 100 = 50

CHARACTER Wren is Keeper               ← fills the slots, now concrete
  voice: female_alto
  home:  Lighthouse
  reputation: 60

No abstract keyword. Abstractness is a consequence of unfilled slots — the compiler refuses to instantiate a declaration with required holes. TRAIT (§9.1) makes that abstractness intentional rather than incidental, but uses the same slot machinery. The pattern shows up in four places:

Beat cast membercast: NPC, Player the caller, at the divert
Beat parameter== ask_about(topic) the caller (with topic: bell)
Scene parameterSCENE patrol(character, route) the spawn site (spawn patrol with character: Wren, route: harbor)
Iteration variable<for: item in Player.inventory> each pass of the loop

9. Three ways to reuse: inheritance, traits, composition

"Composition" in v3 means three different things, and they're easy to confuse. Spelling them out:

MechanismRelationshipSyntaxExample
Inheritance is-a CHILD is PARENT where PARENT is a CHARACTER GoblinKing is Goblin — a GoblinKing is a kind of Goblin
Trait mixing can-do CHILD is TRAIT where TRAIT is a TRAIT Goblin is Looter — a Goblin can be looted
Property composition has-a prop: Type = default loot: LootBag = goblin_pouch — a Goblin has a LootBag

All three play together. The loot-bag example walks through all of them: 

ITEM LootBag                                 ← the thing being owned
  contents: list of ITEM = []
  gold:     int          = 0

ITEM goblin_pouch is LootBag                 ← inheritance on an ITEM
  contents: [rusty_dagger]
  gold:     3

ITEM royal_hoard is LootBag
  contents: [crown, jeweled_dagger, royal_seal]
  gold:     5000

TRAIT Looter                                 ← can-do capability
  loot: LootBag = empty_pouch                ← typed slot + default
  on death
    <drop: loot, at: self.position>

CHARACTER Goblin is Humanoid, Combatant, Looter
  hp:     20
  attack: 4
  loot:   goblin_pouch                       ← override Looter's default

CHARACTER GoblinKing is Goblin               ← is-a Goblin (inheritance)
  hp:     200
  attack: 14
  loot:   royal_hoard                        ← override Goblin's loot

Three mechanisms, three jobs. LootBag is a separately declared ITEM with its own inheritance lineage. Looter is a trait that contributes a typed slot (the loot bag) and the behavior that drops it on death. Goblin inherits from Humanoid + Combatant (concrete templates) and mixes in Looter (capability); it composes a goblin_pouch into the loot slot. GoblinKing inherits from Goblin and overrides the loot to a royal_hoard — three words to spell the difference between a king and a footman.

9.1 What is shares

Whether the right-hand side of is is a CHARACTER, a TRAIT, an ITEM, a STATS profile, a FACTION, or a SCENE, the mechanism is identical: is X, Y pulls in everything X and Y declare — properties with defaults, hooks, generators, goals, scenes, even nested beats. Defaults flow into the child unless overridden. Anything declared on the child by name overrides the inherited version. Required slots must be satisfied or the child stays abstract.

The split between CHARACTER and TRAIT is a contract, not a mechanism: a TRAIT cannot be instantiated standalone (the runtime refuses to spawn one). That's the whole difference. Use CHARACTER when the thing is somebody; use TRAIT when the thing is a capability bundle.

9.2 "Every NPC has a loot bag"

Two ways, pick the one that matches intent:

// Option A: put the slot on the base CHARACTER. Anyone who is an NPC has loot.
CHARACTER NPC
  loot: LootBag = empty_pouch
  ...

CHARACTER Merchant is NPC
  loot: merchant_purse

CHARACTER Goblin is NPC, Combatant
  loot: goblin_pouch

// Option B: put the slot on a trait. Anyone who can be looted has loot.
TRAIT Looter
  loot: LootBag = empty_pouch
  on death
    <drop: loot, at: self.position>

CHARACTER NPC is Looter            ← bake it into every NPC
CHARACTER Merchant is NPC
  loot: merchant_purse

Option A is simpler — one slot, one inheritance edge. Option B decouples the capability ("loseable loot when killed") from the identity ("NPC"), which matters as soon as you want a BossEncounter trait or a Loyalist trait that shouldn't drop loot. Mix the trait where it belongs, not where the inheritance happens to put it.

You can — and usually should — use both at once. The two options aren't exclusive. A mature project typically bakes truly universal capabilities into the base CHARACTER and exposes the rest as traits a character opts into: 
TRAIT Looter         ...   ← capability: can be looted
TRAIT Conversational ...   ← capability: can be spoken to
TRAIT Patrolling     ...   ← capability: walks a route

CHARACTER NPC is Looter, Conversational     ← universals baked in
  ...

CHARACTER Goblin is NPC, Combatant          ← also fights
  loot: goblin_pouch

CHARACTER Loyalist is NPC                   ← still looter + conversational
                                            ← no override needed

CHARACTER Ghost is Conversational           ← skips NPC entirely
                                            ← can talk, can't be looted

The loot slot is the same slot regardless of where it came from. Once a trait or a parent has contributed it, it's just a typed property on the character — children override it the same way, the resolver sees it the same way, hooks read it the same way. There is no runtime distinction between a "trait-contributed" property and an "inherited" property.

Option B is more powerful because it allows opt-out (Ghost simply doesn't is Looter), which Option A can't do without forking the hierarchy. As soon as you're reaching for traits, baking universals into a base CHARACTER becomes the question "do I want this to be optional later?" — and the safe answer is usually yes, so traits win by default in mature projects. 

CHARACTER Humanoid
  hp:    int = 100
  speed: int = 5

CHARACTER Combatant                    ← abstract: hp and attack required
  hp:     int
  attack: int

CHARACTER Bandit is Humanoid, Combatant
  hp:     30                           ← overrides Humanoid.hp; satisfies Combatant.hp
  attack: 8
                                       ← speed inherited from Humanoid (5)

Beats compose the same way; so do stats profiles, scenes, factions, and traits.

9.3 TRAIT — the mixin keyword in full

CHARACTER exists to be instantiated as someone in the world. TRAIT exists to be mixed into characters and other traits. It looks identical — same body, same property syntax, same hooks/generators/goals — but the resolver refuses to instantiate one standalone. The point is to reuse behavior without rewriting it. 

TRAIT Talkative
  chattiness: 0 to 100 = 60                  ← property with default

  generator small_talk
    tier: ambient
    every random(45s, 2m)
      <if: chattiness > 40>
        yield bark from SmalltalkLines

  on meeting Player
    <set: knows.met_player := true>
    -> greet as self

TRAIT Patrolling
  route: list of LOCATION                    ← required slot; no default

  generator walk_route
    tier: ambient
    loop
      for waypoint in route
        <goto: self → waypoint>
        wait until at(waypoint)
        wait random(4s, 10s)

  on cue alarm
    <goto: self → route.first>             ← override-able by name

CHARACTER Guard is Humanoid, Combatant, Patrolling, Talkative
  hp:          80
  attack:      6
  chattiness:  30                            ← override Talkative's default
  route:       [Gate, Wall, Courtyard]       ← satisfy Patrolling's slot

CHARACTER ChattyGuard is Guard
  chattiness:  90                            ← only the thing that's different
                                             ← inherits route, hooks, generator

Now one change to the Patrolling trait re-routes every guard in the show. Adding a new VillageGuard means writing the four lines that are actually different, not re-deriving an NPC from scratch.

9.4 Overrides by name

Everything inside a declaration body has a name — properties (their key), hooks (the leading event clause, normalised), generators (their identifier), goals (their identifier), scenes (their identifier), nested beats (their knot name). A child that declares the same name replaces the parent's version. To extend rather than replace, the child names the parent and calls super: 

CHARACTER ChattyGuard is Guard
  generator small_talk                        ← replaces Talkative.small_talk
    tier: ambient
    every random(15s, 45s)
      yield bark from VeteranWarStories

  on meeting Player
    super                                     ← run inherited body first
    GUARD
      And try not to drip on the flagstones.

9.5 Conflict resolution

When two parents declare a property with different defaults (Humanoid.hp = 100, Veteran.hp = 140), the child must provide an explicit value. Without one the compiler emits an ambiguous slot error. There is no method resolution order to memorise — explicitness over magic.

Hooks compose by source order; if two traits register on meeting Player, both bodies run in the order the traits appear in the is clause. A child can suppress an inherited hook by name: on meeting Player: none.

9.6 The class layer — init, self, method

Every declarable kind in Loom — CHARACTER, TRAIT, ITEM, FACTION, STATS, COHORT, LOCATION, ROLE, SCENE, GENERATOR — is a class. The body declarations (properties, hooks, generators, beats, goals, scenes) are members. Two extra forms turn the class shape into a full object model: init for construction, and method for callable behaviour. Inside either, self refers to the instance under construction or under call. 

STATS Combat
  attribute strength = 10, range 1 to 30
  attribute agility  = 10, range 1 to 30

  init(strength: int? = none, agility: int? = none)
    if strength is not none
      self.strength = strength
    if agility is not none
      self.agility = agility

  axis level
    mode:  xp_curve
    curve: level * level * 50

  pool health
    max:   self.max_health
    regen: 2/s when not self.in_combat

  stat max_health = 50 + self.strength * 5
  stat damage     = 8 + self.strength * 0.5

  method swing(target)
    let blow = self.damage + d6()
    target.health -= blow
    return blow

  method exhausted? = self.health.current < self.health.max * 0.2

Construction happens at the call site. stats: Combat(strength: 12) instantiates a Combat object, runs init with the named args, and binds the result to the enclosing stats slot. The instance lives inside the owning character; it is not flattened. 

CHARACTER Wren is Keeper, Combatant
  stats:    Combat(strength: 12)        ← real constructor call
  loot:     LootBag(gold: 5)
  voice:    female_alto

== bell_strike
  <set: Wren.stats.health -= 4>        ← canonical path
  <if: Wren.stats.exhausted?>          ← method call (`?` predicate name allowed)
    -> collapse as Wren

9.6.1 Dotted access and the embedded-profile fold

Every member of an embedded profile is also reachable directly on the owner — read-only, by name, with the profile's name resolving the collision. The two forms are equivalent for reads: 

Wren.strength            ≡ Wren.stats.strength
Wren.health              ≡ Wren.stats.health.current
Wren.health.max          ≡ Wren.stats.health.max
Wren.damage              ≡ Wren.stats.damage
Wren.swing(Goblin)       ≡ Wren.stats.swing(Goblin)        ← method fold

Writes are not folded: <set: Wren.strength := 14> is a parse-time error pointing at the canonical Wren.stats.strength. Reads fold because authors think "Wren's damage"; writes don't fold because the canonical owner of mutable state must be obvious in the source. The fold also fails — at bundle time — if two embedded profiles export the same name; the author has to write the qualified form.

9.6.2 What self means

self is the bound instance. Inside init it is the object being constructed; inside method, a stat expression, a pool max/regen expression, a hook body, a goal predicate, or any member-scope expression, it is the owning instance. Inside a method on a STATS profile, self.strength resolves to the profile instance, not to the surrounding character; if the method needs its owner, the profile receives it as an implicit argument: self.owner. 

STATS Combat
  method describe()
    return "{self.owner.name} hits for {self.damage}"   ← profile sees its owner

9.6.3 Constructor shorthand

The "strength: 12" form authors used in v2 wasn't wrong — it was just too convenient to give up. v3 keeps it as sugar for the constructor call. An indented property block under a profile slot lowers to a constructor call whose named args are the block keys, in source order: 

// these three forms are identical:
stats: Combat(strength: 12, agility: 14)

stats: Combat
  strength: 12
  agility:  14

stats.strength: 12          ← single-slot override; the rest default
stats.agility:  14

The block form is the friendly default in tutorials; the call form is the one IDEs round-trip and the runtime sees. The dotted form is the convenience for two- or three-line overrides without nesting. All three resolve to the same StatsInstance.

9.6.4 What classes without an init do

A declaration with no init gets a synthesised constructor whose parameters are exactly the kind's writable properties with defaults, in declaration order. Inheritance composes inits the same way it composes hooks: the parent's init runs first (top-down), then each is-mixed trait's, then the child's. super(...) is available inside a child init to pass explicit args up.

10. Simulacra — characters as small simulations

A CHARACTER declaration is the v2 Simulacra package, collapsed into the same syntax as everything else. It carries properties, disposition toward other characters, knowledge, goals, hooks, and generators. None of these need a new bracket; they're indented blocks under the character.

10.1 Disposition

The most-asked-for character depth feature: how does this character feel about that one?

CHARACTER Wren is Keeper
  trusts Player:   30 of 100
  respects Player: 50 of 100
  fears Player:     0 of 100

  reacts trust > 60                          → warm
  reacts fear > 40                           → guarded
  reacts trust < 10 and respect < 30         → hostile

Each X target: N of M line declares a numeric axis bounded 0..M. reacts <cond> → <tag> emits a runtime tag readable in conditions. Mirrors for symmetric relationships: 

  trusts Player: 30 of 100 mirror Player.trusts.Wren

10.2 Knowledge

What this character has learned. A closed schema of typed slots.

CHARACTER Wren
  knows:
    met_player:        bool = false
    bell_origin:       unknown | suspects | confirmed = unknown
    keeper_name:       text?
    rumours:           list of RUMOUR = []
    saw_the_keeper:    bool = false

Mutation surface (only these three):

<set: Wren.knows.bell_origin := suspects>
<set: Wren.knows.rumours += SingingRumour>
<set: Wren.knows.rumours -= SingingRumour>

Knowledge is read-only from outside its character. Every mutation writes a KnowledgeChanged envelope to the ledger; saves round-trip byte-for-byte.

10.3 Goals

What this character is trying to do. Small declarative state machines.

CHARACTER Wren
  goal find_keeper
    priority:       0.8
    active when:    Time.hour > 6 and not Wren.exhausted
    completes when: Wren.knows.saw_the_keeper
    fails when:     Wren.hp < 20
    drives:         search_routine             ← a generator
    on complete:    -> Wren.knows.bell_origin := confirmed
    on fail:        -> log abandoned_find_keeper

Each predicate (active when, completes when, fails when) is reactive — it re-evaluates when its dependencies change, never on a tick. States are dormant → pursuing → (complete | failed); the highest-priority active goal wins. Story can force the machine when it has to: <goal: Wren/find_keeper start>, … complete>, … reset>.

10.4 Hooks — on …

Event-driven character reactions, fired by the ledger.

CHARACTER Wren
  on meeting Player                          ← one-shot encounter
    <if: not Wren.knows.met_player>
      <set: Wren.knows.met_player := true>
      -> introduce_self as Wren

  on trust passes 80                         ← threshold-cross
    -> reveal_secret as Wren

  on Time.hour == 22                         ← in-world clock
    -> retire_for_night as Wren

  on cue bell_strike_loud                    ← crew-bus event
    <set: Wren.knows.heard_the_bell := true>

  on Participant enters Lighthouse           ← location event
    -> greet_visitor as Wren

  on event bell_acknowledged                 ← user-fired event
    <set: Wren.trusts.Player += 10>

The leading clause is matched against the built-in event registry (table identical to v2; the kinds — meeting, passes, drops below, ==, enters, exits, cue, event) carry the same semantics. Edge-triggered predicates fire once per crossing; level-triggered predicates fire once and re-arm only when the predicate becomes false. Hooks never preempt the playhead; they queue and drain at the next yield point.

10.5 Generators on a character

The most direct way to express "what this character does when nobody is talking to them."

CHARACTER Elena
  generator daily_routine
    at 6am   go_to Home
    at 8am   go_to Bakery
    at noon  go_to Harbor

    every random(15m, 45m)
      <if: at Harbor and Weather.fog>
        yield bark from HarborFogChatter

  generator stress_reactions
    when stress > 70
      yield with_chance(0.3)
        ELENA
          (exhausted)
          I need a moment.

A character with no generators is a static prop; one with a few is a village inhabitant; one with a dozen drives an immersive show.

11. Meridian — stats, axes, pools, trees

Stats live on characters or in shared STATS declarations. Five primitives cover every progression model from D&D 5e to Skyrim to Path of Exile, plus "no stats at all" for narrative-only shows. 

STATS Combat
  attribute strength = 10, range 1 to 30
  attribute agility  = 10, range 1 to 30

  axis level
    mode: xp_curve
    curve: level * level * 50
    on advance: <fire: level_up>

  pool health
    max: max_health
    regen: 2/s when not in_combat

  stat max_health = 50 + strength * 5 + Level.lookup(level)
  stat damage     = 8 + strength * 0.5 + (equipped?.bonus or 0)

CHARACTER Wren is Keeper, Combatant
  stats: Combat(strength: 12)                ← real constructor call (see §9.6)

strength: 12 is not a property of Wren — it is a constructor argument to the Combat profile Wren embeds. Wren has a stats slot of type Combat; the embedded profile owns strength. Authors still write Wren.strength in expressions thanks to the read-side fold (§9.6.1), but the source of truth is Wren.stats.strength and that is the path the runtime, ledger, and writes use.

PrimitiveMeaning
attributestatic per-character number set at creation
axisdimension that advances at runtime (six modes: xp_curve, use_tracking, point_buy, milestone, narrative_trigger, sdk_controlled)
poolspendable supply with max / regen / cost
statcomputed or tracked value (expression, lookup table, pool, derived)
TREEDAG of unlockable nodes (own declaration kind, often own file)

Trees as their own file:

stats/WarriorPath.loom
TREE WarriorPath
  node armsman_1
    cost:     { skill_points: 1 }
    requires: axis(one_handed) >= 20
    effect:   stat(damage) += 5

  node armsman_2
    cost:     { skill_points: 1 }
    requires: node(armsman_1)
    effect:   stat(damage) += 5
    effect:   ability PowerAttack

Every Meridian primitive is exposed under dot-path on the character: Wren.strength (attribute), Wren.level (axis), Wren.health (pool current), Wren.health.max (pool max), Wren.damage (stat), Wren.tree.armsman_1? (node presence test). The resolver knows which registry owns the name; no bracket prefixes.

12. Reactive bindings: let, hooks, generators, scenes

The functional layer. None of these need a new bracket — they're declarations or directives — but they're the reason Loom is a scripting language and not a markup format.

12.1 Reactive let

A let is a live formula. Its value updates whenever a dependency changes; conditions that read it subscribe automatically. Backed by prism-core::reactive::Memo<T>. 

let trusted    = Wren.trusts.Player > 50
let in_danger  = Player.health < Player.max_health * 0.3
let crowd_size = count(Participants in BellTower)
let allies     = [c for c in Characters where c.faction == Player.faction]
let nearby     = [c for c in Characters where c.distance(Player) < 10]
let hostile    = [c for c in nearby where c.disposition(Player) is hostile]

Conditions are bare names — <if: trusted>. The same form is allowed at any scope: top of file (project-global), inside a beat (beat-local), inside a scene (scene-local).

12.2 Ledger queries

Time and history are expressions. The ledger is one append-only stream; queries are read against per-entity views materialised over it. 

<if: since(bell_rung) < 30s>          ← show-global
<if: since(Participant, bell_rung) < 30s>  ← scoped to one participant
<if: last(Wren, speaker) == Player>       ← Wren's view
<if: visits(opening) == 1>                ← visit counter
<if: played(intro)>                       ← any-time predicate

12.3 Scenes

A SCENE is a labelled coroutine — a multi-step interaction with explicit state transitions. Where a generator yields ambient content, a scene drives a focused exchange. 

SCENE patrol(character, route)
  for waypoint in route
    <goto: character → waypoint>
    wait until character.at(waypoint)
    wait random(3s, 8s)

    <if: character.spotted_intruder>
      -> investigate as character
      return

SCENE investigate(character)
  approach
    <set: character.disposition(Player).suspicion += 5>
    wait until character.at(Player.position)
    -> examine

  examine
    NPC
      (focused)
      Hmm. Something's not right.
    wait random(2s, 4s)
    <if: character.deduction > 60>
      -> confront
    -> withdraw

  confront
    <fire: character.investigated with target: Player, result: clue>
    return clue

  withdraw
    <fire: character.investigated with target: Player, result: none>
    return none

Scenes have parameters, labelled states (the inner bare-name blocks), wait, yield, return. Invoked via spawn patrol with character: Wren, route: harbor (fire-and-forget) or let r = run investigate(character: Wren) (await return value).

12.4 Generators

Long-running coroutines that yield content to the runtime.

GENERATOR HarborChorus
  tier:     ambient
  priority: 0.3

  loop
    wait random(20s, 60s)

    <if: Storm.active>
      DOCKHAND | FISHER
        (worried)
        <shuffle: Storm's close. | Sky's wrong. | Time to tie down.>

    <else if: Bell.ringing>
      VILLAGER
        (surprised)
        The bell! It's ringing!

    <else>
      FISHER | VILLAGER
        <cycle: Quiet night. | Stars are out. | Tide's calm.>

Generators run until cancelled. The runtime starts named generators on boot or via <spawn: HarborChorus>. Multiple generators run concurrently. They are character-bound (declared inside a CHARACTER) or world-bound (top-level).

12.5 Tiered scheduling

Round-robin breaks at scale. Every generator and scene runs in one of three tiers:

TierWhen it ticksDefault population
focalevery frameactive conversation; scenes the camera/PoV is in
activeevery ~100msnearby NPCs; characters the player has spoken with recently
ambientevery ~2sdistant NPCs; world generators; village background

Each tier has a per-tick budget. Author override is always explicit on the declaration (tier:, priority:). A scene marked tier: focal is never deferred — the scheduler steals from active and ambient before dropping a focal frame.

13. Live performance — roles, people, rosters, cast

v2 hard-coded "audience member" as PARTICIPANT and left scripted characters in a separate world. That split breaks the moment a show has any of: an actor playing a named role, an audience member promoted into a named role mid-show, a swing performer covering someone who didn't arrive, an AI agent driving an NPC. Real non-linear multi-participant theatre needs one model where the role and the person playing it are different things, freely re-bindable, and both inspectable.

v3 collapses the live-performance surface into four nouns:

NounIsLifespanExample
ROLE A scripted character template — class, props, hooks, goals, stats. The fictional entity. Compile-time. Reusable. ROLE Wren is Keeper, Combatant
PERSON A real human (or AI agent) the show knows about — pronouns, devices, accessibility, contact, schedule. Persistent. Survives shows. PERSON jamie_lee
ROSTER A planned line-up for a specific run — who is expected, in what role, in what cohort, with what swings. Pre-event → showtime. ROSTER preview_night_05_28
CAST The runtime binding "person X is currently playing role Y." Live, mutable, ledger-backed. Showtime only. <cast: jamie_lee as Wren>

CHARACTER is an alias for ROLE — every existing CHARACTER Wren is … stays valid, and a project may mix the two keywords freely. The doc uses ROLE below because it makes the model legible; tutorials and the friendly reference use CHARACTER because that's what writers already type.

PARTICIPANT stops being a kind. The phrase as Participant still works inside hooks and diverts — it's now an alias for "the person this event is about" (§13.5). The generic, name-less "audience member" case is just a PERSON with no ROLE bound, or with the synthetic ROLE Audience that every project gets for free.

13.1 ROLE — the fictional entity

A ROLE is exactly what CHARACTER always was: a class (§9.6) with props, stats, hooks, goals, generators, beats. It has no inherent notion of who is playing it. A role can be played by an AI agent driving NPC behaviour, by a credited performer, by a swing, by an audience member who was promoted into it, by nobody at all (a "ghost" presence that fires hooks but produces no output). Everything in §9 and §10 applies. 

ROLE Wren is Keeper, Combatant
  voice:        female_alto
  stats:        Combat(strength: 12)
  trusts Player: 30 of 100

  on meeting Player
    -> introduce_self as self          ← self = the role's bound instance

13.2 PERSON — the real human

A PERSON is a class too, but its properties model the human, not the fiction: pronouns, display name, accessibility notes, device address, content tolerances, schedule. Persons live in the project (the company's people/ folder) and survive individual runs. 

PERSON jamie_lee
  display_name:    Jamie Lee
  pronouns:        they/them
  email:           jamie@example.com
  device:          jamie_phone_01
  content_tolerance: [no_strobe, no_loud_bells]
  accessibility:   [step_free]
  notes:           Veteran swing. Comfortable in the Bell Tower.

PERSON anonymous_walkup       ← audience members get a per-show PERSON minted
  display_name:    Guest 12
  device:          wristband_12

The minimal PERSON is just a display_name + a device (or no device at all — purely physical attendance). Every other field is optional. Walk-up audience members are minted into ephemeral PERSONs at the door — a kiosk, the booth, or a join handshake — and the runtime treats them identically to known performers. The split between "audience" and "cast" is a binding, not a kind.

13.3 ROSTER — planning a specific run

A ROSTER is the rehearsal-and-houseplan view: for this performance, who is expected to play what, who covers whom, who starts where. Rosters are first-class declarations so they round-trip into the booth UI, into the simulator, into export. 

ROSTER preview_night_05_28
  date:     2026-05-28T19:30
  capacity: 24

  cast
    Wren        := jamie_lee
    Bellkeeper  := raja_park
    Initiate    := any of [audience]        ← role filled by walk-ups
    Singer      := any of [pat_eberle, kim_ho, audience]

  swings
    Wren        := [raja_park, kim_ho]      ← covers in priority order
    Bellkeeper  := [jamie_lee]

  cohorts
    Initiates   start with: [audience]
    Singers     start with: [pat_eberle, kim_ho]

  locations
    BellTower   start with: [jamie_lee]     ← pre-show placement

  notes
    raja_park:     Late call — orientation skip if not in by 19:25
    no_strobe:     Honour PERSON.content_tolerance during act two

Roster slots accept concrete bindings (a named PERSON), open holes (any of [...] — a set of acceptable PERSONs, or the synthetic set audience for any walk-up), and swing chains (priority-ordered fallbacks). A roster slot left empty is legal — it just means the role plays as a "ghost" until someone is cast in. Diagnostics flag a roster whose holes can't be filled by its declared pool, but never refuse to load — the booth must be able to open a show with gaps and fix them at the door.

Loading a roster at showtime is one directive: <load_roster: preview_night_05_28>. The runtime walks the cast block and emits CastBound envelopes for each concrete binding, CastHoleOpened envelopes for each unfilled hole. The booth UI lists the holes and offers per-PERSON fill from the live attendance set.

13.4 CAST — runtime binding

At runtime, the binding "person ↔ role" is mutable state owned by the CastRegistry. Every relevant operation is a directive with a ledger envelope:

DirectiveEffectLedger
<cast: jamie_lee as Wren> bind jamie_lee to Wren CastBound
<uncast: Wren> release Wren's binding; role plays as ghost CastReleased
<recast: Wren := kim_ho> atomic swap (preserves running scenes, stats, goals) CastSwapped
<promote: anonymous_walkup_12 as Initiate> turn a walk-up audience PERSON into a named role mid-show CastBound + RolePromoted
<demote: kim_ho> kim_ho stops playing whatever role; remains a PERSON in attendance CastReleased
<enroll: jamie_lee → Initiates> cohort membership (unchanged from v2) CohortEnrolled

Recast is the deep one: the role's stats, goals, hooks, and any in-flight scene/generator stay alive. Only the player changes. This is what lets a director swap a fainted performer mid-act without losing the show's running state.

13.5 The as Participant alias

In a hook or a divert, Participant resolves to "the PERSON this event is about" — the joiner of a join event, the mover of a location event, the audience member whose device tapped a cue. It's a binding name, not a type. The scoped-beat form (-> orientation as Participant) overlays self = that PERSON inside the target beat, so expressions like self.display_name, self.content_tolerance, or self.role.trust(Player) all resolve. 

on participant joins
  <enroll: Participant → Initiates>
  -> orientation as Participant         ← inside, `self` is that PERSON

== orientation
  cast: self
  <if: self.content_tolerance contains no_strobe>
    -> gentle_intro as self
  -> standard_intro as self

When the PERSON is also currently playing a ROLE, both faces are addressable: self is the PERSON, self.role is the ROLE instance they're bound to (or none if they're unbound audience). The reverse exists too: from a ROLE-scoped beat, self.player is the PERSON currently cast in it. Both can be none — a PERSON not playing a role; a role with no player. Authors test with self.role? / self.player?.

13.6 Presence — locations and cohorts on PERSONs

Location and cohort membership belong to the person, not the role. (Re-casting a fainted Wren to a swing doesn't teleport Wren's body across the venue.) LOCATION and COHORT retain their existing declarations and capacity semantics from v2; the only change is that membership lookups now go through PERSON: 

count(jamie_lee in BellTower)         ← presence query
[p for p in Persons where p in Initiates and p.role? is Initiate]
self.player.location                  ← from inside a ROLE method
Wren.player?.device                   ← may be none if no one is cast

13.7 Cohorts and locations

COHORT Initiates
  label:    The Initiates
  capacity: 24

LOCATION BellTower
  label:    The Bell Tower
  capacity: 12

on participant enters BellTower
  -> bell_first_visit as Participant

Same syntax as v2. The only thing that changed underneath is what a "participant" is: a PERSON, not a separate kind.

13.8 Broadcast scopes

<broadcast: participant(Participant)>
  NARRATOR
    (whispering)
    You hear it differently. You always have.

<broadcast: location(BellTower) but participant(Participant)>
  NARRATOR
    The others look up.

<broadcast: cohort(Singers) and location(BellTower)>
  <cue: private_choir>

Scope atoms compose with and (intersection) and but (difference). The runtime applies the filter to the broadcast's content stream.

13.9 Improv with pluggable advancement

BELLKEEPER
  (improv duration: 45s, advance on: any [pedal, speech(anchor phrase), gesture(Bow)])
  (Greet warmly. Find out why they came. Don't reveal the singing —
   that's act two.)

  -> next_beat

The parenthetical body is a directive to the performer (the parens keep it out of the spoken line). The runtime displays it on the performer's prompter, holds the playhead until any configured signal arrives or duration elapses, and writes ImprovBeatStarted / Advanced envelopes to the ledger. Quorum operators (all, any, quorum(N)) match v2.

13.10 Live patching from the booth

The booth and simulator both bind the same panel surface (§13.11) on top of the runtime; "live patching" is just the operator side of inspection. Below is what the operator can do.

The booth UI — a Prism app on the same LoomRuntime — can skip a PERSON past a beat, force-fire a cue, recast a role, uncast a person who left, promote a walk-up, hot-reload a .loom patch without stopping the show. Every booth action is a Loro CRDT op on the same store. The booth is just another client.

13.11 Inspection panels — simulator and runtime parity

The simulator (rehearsal-time) and the runtime booth (showtime) share one inspection surface. Both bind to the same registries; the only difference is whether time is mocked or real. The surface is built out of four panels, each of which addresses the model the same way whether you are sitting at a sim or running the show.

PanelListsDrill-in shows
People Every PERSON the runtime knows about display name, pronouns, content tolerances, device status, current location, cohort memberships, current cast binding (self.role), recent ledger envelopes about them
Roles Every ROLE declared in the bundle (concrete + abstract) stats (with embedded profile fold), disposition matrix, knowledge schema state, active goal + goal queue, recent hooks fired, current player (self.player), in-flight scenes/generators
Roster The loaded ROSTER + its swing chains + the live cast registry hole status (filled / open / contested), swap history, recast suggestions from swing chains, one-click cast/uncast/recast/promote
Stage Locations + cohorts capacity vs. occupancy, who is where (PERSON list with their bound role inline), broadcast-scope preview, pending improv beats

Each panel row exposes a context object whose dotted paths are the same the language sees. The Roles panel selecting Wren binds self = Wren for the side pane; expressions evaluable in the language (self.stats.health, self.player.display_name, self.goals.find_keeper.state) are exactly what the inspector reads. No second model, no fixture-shaped DTO between the runtime and the panel.

The People panel is the side that v2 never had a clean answer for: it is where the operator sees that Jamie Lee (PERSON) is currently playing Wren (ROLE), is standing in the BellTower, is enrolled in Initiates, has flagged no_strobe as a content tolerance, and last triggered a bell_strike cue. The Roles panel is the same data viewed through the fiction: Wren has 12 strength, is pursuing the find_keeper goal, is currently played by Jamie Lee. Pick whichever face the moment needs.

14. Runtime directives — Luau function calls

A directive <kind: args> is a call to a Luau function named kind. The colon separates the function name from its argument list; commas separate positional args; named args use name: value. The runtime ships a core registry of directive functions (audio, lighting, mutation, control flow, scope) and Loom adopts whatever else a studio's Luau extensions register. 

// runtime/audio.luau
directive sfx(name: string, fade: number?)
  audio.play(name, { fade = fade or 0 })
end

directive cue(name: string)
  bus:fire("cue", { name = name })
end

// studios/saltmere/extensions.luau
directive flash(color: string, duration_ms: number)
  lighting.flash(color, duration_ms)
end

directive heal(target: Character, amount: number)
  target.health = math.min(target.health + amount, target.max_health)
  ledger:append("Healed", { target = target.id, amount = amount })
end

And in a beat:

WREN
  (startled)
  Lightning?<flash: white, 200>

She raises the lantern.<heal: Wren, 10>

No distinction between core and user-defined. The same registry, the same dispatch. A Loom file that calls <flash:> with no flash registered is a build error from the resolver, identical to a missing function in any other language.

14.1 The argument convention

The Loom-side <kind: a, b, key: value> maps to the Luau-side kind(a, b, { key = value }) — positional args first, named args collected into a trailing table. A bare <kind> is a nullary call. Multi-line block-opening directives pass their body as a Luau closure: 

directive broadcast(scope: Scope, body: () -> ())
  with bus:scoped(scope) do
    body()
  end
end

// usage:
<broadcast: location(BellTower)>
  NARRATOR
    The bell groans on its mounting.

14.2 The small set of syntactic forms

A few directives cannot be plain Luau functions because they affect the parser's scope rules or the playhead's structure. These are syntactic forms baked into the grammar; they happen to share the <…> bracket for consistency but the parser handles them, not a registry lookup.

FormWhy it's syntactic
<if:> / <else if:> / <else> introduces conditional weave branches the playhead must traverse
<match:> multi-arm dispatch over an expression; each arm is a weave branch
<for:> introduces a loop variable into lexical scope
<each visit> with first / then / finally visit counter drives arm selection — needs ledger access at parse time
<after:> / <otherwise> state-morphing block: once cond turns true, the after body replaces the rest of the beat for this playhead
<anchor:> names a position in the weave (tests jump here); needs static visibility
<let:> introduces a binding into lexical scope

Everything else — sfx, cue, set, fire, pause, shuffle, cycle, spawn, cancel, goal, broadcast, enroll, goto, compose — ships as a Luau function in the core registry, and any studio can replace, extend, or shadow it.

14.3 LSP completion

Because directives are registered functions, the LSP autocompletes from the project's loaded registry — core + every Luau extension on disk. Signature help shows the Luau function's parameter list. Jump-to-definition lands on the directive kind(...) declaration. Hover documentation is whatever Luaudoc-style comment sits above the function.

Anchors are first-class. <anchor: name> is the v3 testing primitive. Tests jump to anchors, analytics count how many players reach them, links cross-reference them, the authoring tool's "skip to here" affordance uses them. Lift anchors liberally — they're cheap.

15. Production metadata — ``` … ```

The prompt-book column, lifted inline as a Markdown-style fenced block. The runtime parses it and does nothing at production. It exists for stage managers, producers, authors, and debuggers. The first token names the kind; tooling filters on it.

Two forms, identical in meaning, used as legibility dictates:

  • Inline — one line, opening and closing fence on the same line: ```warn lx14```.
  • Block — opening fence on its own line, free text or further structure below, closing fence on its own line.
```warn lx14```
```warn sq7```

WREN
  (quietly)
  It hasn't rung in three days.
  ```blocking: cross DSR on "rang"```

```lx14 go```
```sq7 go on "Mitch"```

```note
This scene felt long at the table read. Try cutting the lantern beat;
the silence after the bell carries more than the dialogue.
```

```todo: confirm with director that the silence after the bell holds```
```break: trust >= 80```                    ← debugger conditional breakpoint
```related: Wren/backstory```

Borrowing the Markdown fence has three immediate wins. First, every writer who has touched GitHub, Discord, Notion, or Obsidian already knows what triple-backticks do — an out-of-band region. Second, syntax highlighters that don't know Loom still grey it out correctly, because they treat it as a code fence. Third, the fence language tag (the word after the opening backticks) is exactly the metadata kind — ```warn reads naturally as both "this is a warn" and "this fence is tagged warn".

The first token inside the fence is the metadata kind; tooling filters on it (warn, cue, blocking, note, todo, break, related, …). The kind set is open — production teams invent conventions and the LSP suggests from the workspace's history.

17. Implementation notes

v3 is the only Loom that ships. The v2 parser, runtime, LSP, syntax tooling, and lesson corpus were deleted at the start of the v3 cutover — there is no version flag, no dual parser, no shared IR with a legacy path. Anything from v2 worth keeping (Simulacra disposition, Meridian primitives, ledger envelope shapes, the LSP's tmgrammar scaffolding) is being re-grown inside the v3 design rather than bridged.

  1. Crate layout. Everything Loom lives under packages/loom/: parser (lexer + AST + diagnostics), runtime (bundle, resolver, playhead, ledger, reactive graph, scheduler), lsp (stdio JSON-RPC server backed by the parser + workspace index), and syntax (the TextMate grammar plus the Zed / VSCode extension scaffolding). The five-bracket discipline drives the grammar and the scope names alike.
  2. Directive registry. The runtime ships a core Luau registry under packages/loom/runtime/src/builtins/ (audio, lighting, mutation, control-flow, scope, anchor). Studio-specific verbs land in a workspace's extensions/ folder and are loaded at boot.
  3. Project model. A project is a folder rooted at main.loom; names resolve flat across the whole workspace. The resolver indexes every .loom file on load, and divert resolution errors loudly on ambiguity rather than guessing (see §18).
  4. Reference examples. The lesson corpus is rebuilt from scratch as v3-native — typed slots, multi-file projects, the reactive layer, the live layer — under packages/loom/examples/.
  5. Tooling. The TextMate grammar at packages/loom/syntax/loom.tmLanguage.json carries five bracket scopes — (), {}, [], <…>, ``` … ``` — and the LSP carries project-aware completion (every CHARACTER, every TRAIT, every registered directive function, every beat, every anchor, every ```todo``` fence in the workspace).

18. Open questions

  • Divert ambiguity resolution. When two beats in different files share a name, do we error and force the writer to qualify (Lighthouse/ringing), or pick by some heuristic (closest in the folder tree, most-recently-touched)? Leaning error — silent guessing is the worst failure mode for narrative tools.
  • File-level cast: shorthand. Should a file declare a default cast that all its beats inherit, so the per-beat cast: can be omitted? Leans yes for character-centric files (cast/Wren.loom); leans no for hub files. Probably both, with an explicit per-beat override.
  • Hot-reload granularity. Editing cast/Wren.loom mid-show — do all in-flight hooks finish under the old definition, or rebind at the next ledger flush? v2 chose "finish under the old"; keeping that is the safer default but worth re-confirming with live operators.
  • Reactive let visibility across files. A let in main.loom is project-global by default. Should files be able to declare lets that are file-local (not visible to other files)? Leaning yes via a local let form, but the common case is the global one.

19. Acknowledgements

Every idea here descends from somewhere older. The five-bracket discipline and the multi-file project model are v3's only contributions. Everything else is recombination — screenplay's positional formatting, Fountain's inference-with-escape, Ink's == / * / + / -> vocabulary and the […] suppress trick, Twine's passage-as-file model, Obsidian/Logseq's local-first identity, fine- grained reactivity from the Solid/S.js lineage, the prompt-book column from a hundred years of stage management, and the character / stat / faction model that v2 built as Simulacra and Meridian. The weave / loom / thread metaphor predates all of them and is the project's reason for being.
