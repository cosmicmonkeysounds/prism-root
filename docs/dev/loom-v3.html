Loom v3 design

Loom is not a programming language. It is a format — a way of writing down a story, its production, and the systems that weave them together, all in one local-first plain-text file. Writers read it as a screenplay. Stage managers read it as a prompt book. Producers read it as a breakdown. The runtime reads it as a program. v3 commits to that promise.

The three claims.
  1. The format is a screenplay. Position, capitalisation, and indentation carry meaning. Quotes, apostrophes, and most punctuation belong to the writer. We borrow the 1920s screenplay convention, Fountain's plain-text-with-escapes discipline, and Ink's branching vocabulary — wholesale.
  2. Five brackets, five audiences. The performer, the reader, the choice-list, the runtime, the production team. Each has its own bracket; none share. (See §4.)
  3. Generics are typed slots. One mechanism covers cast members, parameters, iteration variables, and object properties. There is no trait, no template, no macro, no extends. There is one composition verb, is, and one execution model, top-down with branches.

1. The lineage — six formats v3 descends from

Every choice below is an inheritance from a tradition older than this document. Knowing which is which is the cheat sheet for understanding v3.

TraditionWhat v3 takes
Stage scripts (Samuel French / Dramatists, BBC radio, prompt books) The parallel cue column. Production metadata lives next to text, not inside it. v3's <<…>> bracket is that column, lifted into the same file.
Hollywood screenplay (Academy/WGA, ~1920s) Position-is-syntax: ALL CAPS speaker cues, indented dialogue, parenthetical directions in (parens), action lines flush left, scene headings INT./EXT.
Fountain (Maschwitz/August, 2012) Plain-text screenplay with inference and escape: defaults are positional; sigils (., @, !, >) only appear when the writer needs to override the inference. v3 follows the same discipline — a writer who knows screenplay formatting knows v3 prose.
Ink (inkle Studios, 2016 — used in 80 Days, Heaven's Vault) Knots (==), choices (* once, + sticky), diverts (->), gathers (-), and the choice-suppress trick […] — the same line serves the choice list and the narration output. All four are imported verbatim.
Twine (Klimas, 2009) The passage as a file unit AND a graph node. A beat in v3 can live as its own .loom file, identified by name, addressable by any other file — the Twine/Obsidian "everything is a file" instinct.
Obsidian / Logseq (local-first plain-text notes, 2020+) Identity by filename, emergent backlinks from bare [[wiki links]] (in v3: bare Capitalised names auto-link), inline key: value properties (no YAML frontmatter required). Prism's parent inspiration; Loom inherits it.

v3 contributes one new thing: the five-bracket discipline (§4). Everything else is recombination of patterns that have already shipped somewhere.

2. Loom as a format, not a syntax

A syntax requires you to think in tokens, delimiters, escapes. A format is something a human reads and understands without parsing. Markdown is a format. Fountain is a format. Loom v3 is a format with one extra promise: the same file is the writer's screenplay, the stage manager's prompt book, the producer's breakdown, and the runtime's program.

Concretely, this commits us to four rules:

  1. Quotes belong to the writer. ", ', «, " never appear in the grammar. A writer can paste any dialogue verbatim, including contractions and quoted speech, and it parses.
  2. Position over delimiters where position works. A name on its own line is a speaker. An indented line under a speaker is dialogue. A paragraph at the left margin is action. A line starting with * or + is a choice. These are all positional — exactly as screenplay has done for a century.
  3. Brackets, when used, mean one thing each. Five bracket shapes, five distinct jobs, no overlap. §4.
  4. Printable on paper. A .loom file printed and handed to a director should be directable. Any line that exists for the machine alone is in <<…>> (sidecar metadata) so a producer can mark it as "ignore at the table read".

3. The imperative weave

Loom is an imperative language. A beat is read top-to-bottom; the playhead advances through prose, dialogue, and cues; branches fork at choices and diverts. State (variables, disposition, knowledge) is mutated by explicit actions. There is no reactive graph, no declarative truth-maintenance.

A "weave" is the branching graph traced by all possible playheads through the document. The writer authors moments in order; the runtime weaves them into a thread for each playthrough. This is the same execution model as Ink, Twine, and most screenplay-shaped narrative engines.

4.1 ( … ) — the performer

Parens are reserved for what an actor performs. The 1920s screenplay convention: a parenthetical sits indented under a speaker, in lowercase, describing manner or action. 

WREN
  (quietly)
  It hasn't rung in three days.
  (she turns the lantern up)

Outside a speaker block, parens describe a stage action that any performer in scene executes — the "she crosses DSR" of a stage script. Inside prose narration parens are literal text; a writer uses them freely. The parser knows the difference by position: a (lowercased phrase) on a line by itself, indented under a speaker or at action depth, is a directive. A paragraph that happens to contain "(an aside)" mid-sentence is just prose.

4.2 { … } — the reader (value)

Curly braces always evaluate to a value substituted into the surrounding text. Nothing else lives here. 

PLAYER
  I have {coins} coins and {Player.inventory.length} items.

WREN
  Welcome back, {Player.name}.

4.3 [ … ] — the reader (hidden)

Lifted verbatim from Ink. Text inside square brackets appears in the choice list only; text after the brackets appears in the narration output only; text before appears in both. 

* "There is not a moment to lose!"[] I declared.
  -> hurry_outside

* "Monsieur, let us savour this moment."[] I declared.
  -> dragged_outside

This earns its own bracket because no other tradition has solved the "the same utterance reads differently in the menu vs. the playback" problem so compactly.

4.4 < … > — the runtime

Single angle brackets fire something at the runtime. Side effects, state mutation, control flow blocks, testing anchors. All inline or on their own line. The directive's first token names its kind; a colon separates the kind from its arguments. 

WREN
  The bell... <sfx: ding> it's ringing.

<set: trust += 10>
<fire: bell_acknowledged>
<anchor: bell_moment>          ← bookmark for testing / replay / linking

<if: Player.has key>
  Player unlocks the door.
<else>
  WREN
    You'll need a key.

<shuffle: Hi | Hello | Hey> there.

Inline directives in dialogue (<sfx: ding>, <pause: 1s>, <set: x += 1>) fire at the typewriter reveal point — useful for syncing sound with a line, mutating state mid-sentence, or planting a named <anchor: …> for tests to jump to.

The full set of directive kinds is enumerated in §8.

4.5 << … >> — the production team

Doubled angle brackets are passive metadata. The runtime ignores them. They exist for stage managers, producers, debuggers, and the author's own notes. The prompt-book convention, brought inline. 

<<warn lx14>>
WREN
  (quietly)
  It hasn't rung in three days.
  <<blocking: cross DSR on "rang">>
<<lx14 go>>

<<note: this scene felt long at the table read — try cutting the lantern beat>>

She turns the lantern up.

The split between <…> and <<…>> is does the runtime do something with it? A sound cue fires at production — that's <sfx:>. A warning to the lighting board four lines before the actual cue — that's <<warn lx14>>. An author note about pacing is purely <<…>>.

5. A .loom file

Two zones, mixed freely.

# Lighthouse Dawn
loom: 3
entry: opening

#  Declarations  ─────────────────────────────────

CHARACTER Wren is Keeper, Combatant
  voice: female_alto
  home:  Lighthouse
  hp:    80
  attack: 4
  has:   brass_lantern
  knows: bell_origin

  trusts Player:  30 of 100
  respects Player: 50 of 100

CHARACTER Player is Visitor

ITEM brass_lantern
  weight: 2
  fuel:   75 of 100

LOCATION Lighthouse
  ambient:  wind_low
  contains: bell_rope, brass_lantern

#  Beats  ─────────────────────────────────────────

== opening
  cast: Wren, Player
  setting: Lighthouse

INT. LIGHTHOUSE - DAWN

A bell rope swings in the gloom. Wren watches it from the doorway.

WREN
  (quietly)
  It hasn't rung in three days.

She turns the lantern up.

* Ring the bell.
  -> ring_bell
+ Ask about the keepers.
  -> ask_about with topic: keepers, NPC: Wren

The structural conventions:

  • Header — a Markdown-style # Title plus a few key: value properties (loom: 3, entry: knot_name, tags: …).
  • Declarations — CHARACTER, ITEM, LOCATION, FACTION, ENTITY (the unopinionated base). Each is a named block of key: value properties plus optional composition (is X, Y).
  • Beats — == knot_name introduces an imperative beat. Contract follows (cast:, setting:, uses:), then the woven body (prose, dialogue, choices, diverts, directives).
  • Scene headings — Fountain-style INT. LOCATION - TIME lines. Pure atmosphere — they tell a director and a reader where we are. They do not define structure; == does that.

6. Typed slots — the one generic mechanism

Generics in non-linear narrative happen at every scale. A merchant beat works for any merchant. A guard character template instantiates any guard. A recognition scene needs a mentor and a mentee. All of these are the same shape: a typed slot, filled at the call site.

6.1 The pattern

A typed slot is a property declaration with no default. The declaration is abstract until every required slot is filled; concrete the moment the last one resolves. 

CHARACTER Keeper                       ← abstract: voice has no default
  voice: any
  home:  any of LOCATION
  reputation: 0 to 100 = 50

CHARACTER Wren is Keeper               ← fills the slots, now concrete
  voice: female_alto
  home:  Lighthouse
  reputation: 60

No trait keyword. No abstract keyword. Abstractness is a consequence of unfilled slots — the same way arithmetic on undefined values is a consequence, not a separate feature. The compiler refuses to instantiate Keeper directly because voice has no value; it instantiates Wren happily.

6.2 The same pattern, four places

WhereLooks likeFilled by
Object property voice: any a child declaration (via is) or instantiation override
Beat cast member cast: NPC, Player the caller, at the divert
Beat parameter == ask_about(topic) the caller (with topic: keepers)
Iteration variable <for: item in Player.inventory> each pass of the loop binds item

All four are "a name introduced in a header, used bare in the body". Resolution is lexical: the parser knows what topic means inside a beat declared with (topic); it knows what item means inside the <for:> block; it knows what Wren means after cast: Wren.

6.3 What goes in a slot type

7. Composition: is

One verb. is X, Y pulls in the property declarations of X and Y. When a slot in X has a default, that default flows into the child unless overridden. When a slot has no default, the child must provide one (or remain abstract itself). 

CHARACTER Humanoid
  hp:    int = 100
  speed: int = 5

CHARACTER Combatant                    ← abstract: hp and attack required
  hp:     int
  attack: int

CHARACTER Bandit is Humanoid, Combatant
  hp:     30                           ← satisfies Combatant.hp + overrides Humanoid.hp
  attack: 8                            ← satisfies Combatant.attack
                                       ← speed inherited from Humanoid (5)

Conflicts between two parents (both declare hp with different defaults) are resolved by the child providing an explicit value. Without one, the compiler emits an "ambiguous slot" error. There is no method resolution order to memorise; there is no inheritance chain to walk; is is set union with override.

Beats compose the same way:

== greeting
  cast: NPC, Player
  setting: any
  NPC
    Hello.

== formal_greeting is greeting
  NPC
    Good day to you.                   ← inherits cast/setting, replaces body

8. Runtime directives — <…>

Every directive is <kind: args> (or <kind> for nullary). The kind names the operation; args follow a colon. Block-opening directives have an indented body and end at dedent.

KindFormEffect
sfx<sfx: bell-toll>fire a sound effect (inline or block-level)
cue<cue: lights_up>fire a named crew cue (lighting, projection, machine)
set<set: trust += 10>mutate a variable or property
fire<fire: bell_acknowledged>fire a named event onto the bus
anchor<anchor: bell_moment>name this point in the weave — tests jump here, replays bookmark here, linkbacks point here
pause<pause: 2s>delay the next reveal
shuffle / cycle / once / random<shuffle: a | b | c> or block formruntime selects from alternatives (Ink-flavoured)
if / else<if: cond> ... <else>conditional block
match<match: expr>multi-arm block
for<for: item in xs>iteration block
spawn<spawn: Bandit with rank: 2>create a runtime instance of a template
Anchors are first-class. <anchor: name> is the v3 testing primitive. Any anchor is addressable from tests (play_to(@bell_moment)), from analytics (count how many players reach this point), from linkbacks (other documents cross-referencing @bell_moment), and from authoring (the editor's "skip to here" affordance). Lift anchors liberally — they're cheap and they pay off everywhere.

9. Production metadata — <<…>>

<<…>> is the prompt-book column, lifted into the file. The runtime parses it but does nothing at production. It exists so that:

  • Stage managers can mark blocking, warns, cues, and standbys without polluting the spoken text.
  • Producers can break the script down — flag props, set pieces, costume changes — using filterable tags.
  • Authors can leave notes-to-self, todos, table-read feedback, structural reminders.
  • Debugging can drop conditional breakpoints, watches, and trace markers that the runtime can opt into at debug-time but ignores in production.
<<warn lx14>>
<<warn sq7>>

WREN
  (quietly)
  It hasn't rung in three days.
  <<blocking: cross DSR on "rang">>

<<lx14 go>>
<<sq7 go on "Mitch">>

<<note: this scene felt long at the table read — try cutting the lantern beat>>
<<todo: confirm with director that the silence after the bell holds>>
<<break: trust >= 80>>     ← debugger conditional breakpoint

The first token inside <<…>> is the metadata kind. Tooling can filter on it: "show me all blocking: notes for act 1", "list every todo:", "highlight every warn: in the prompt view". The runtime itself reads them only to forward to consumers (debug protocol, prompt-book view, breakdown report).

10. Prism + Obsidian: local-first, linked

Loom files live inside a Prism workspace. Three integration points matter.

10.1 Files are the identity

Each CHARACTER or ITEM or LOCATION may live in its own file — cast/Wren.loom, items/brass_lantern.loom, locations/Lighthouse.loom. Or many declarations can sit in one file. The bare name in another file resolves the same way either way; the resolver walks the workspace tree and picks the declaration with the matching name. Twine and Obsidian both work this way; v3 follows.

10.2 Backlinks are emergent

When a beat mentions Wren in prose, that's a backlink. When a beat diverts to -> ring_bell, that's a backlink. When metadata mentions <<related: Wren's Backstory>>, that's a backlink. Prism harvests them all and shows the inverse — "every place that mentions Wren" — without the writer having to maintain it.

10.3 The Prism runtime

packages/prism-loom-runtime/ already exists. v3 lands as a new parser path behind a loom: 3 header property; v2 files continue to compile through the v2 path. Both lower to a shared bundle IR, so the playhead, ledger, hook system, and disposition machinery are reused unchanged. The new modules are objects.rs (unified declaration registry), directives.rs (one dispatcher for every <kind:>), and metadata.rs (read-only sidecar parsing). Loom's LSP (packages/prism-loom-lsp/) follows the same split.

11. What v2 had that v3 doesn't

v2v3Why
Sigils $, @, [[ ]] None. Bare capitalised names link; lexical scope resolves. Position and capitalisation carry the same information.
Quote-delimited strings "…" / '…' None. Tail-of-: for properties; indented prose for dialogue. Quote characters belong to the writer.
{quietly} as a speaker emotion bracket (quietly) on its own line — screenplay convention. Curly braces are reserved for value substitution. Performer notes are parens, as they have been for a century.
match + after/otherwise <if:> + <match:>. Two forms. Two control verbs cover every case.
~ action action lines <set:>, <fire:>, <cue:> directives. One bracket discipline for everything the runtime executes.
Inline $(s-expr) Gone. Use {expr} for values. One value-substitution form.
Generators (barks, routines, improv) <shuffle:>, <cycle:>, <random:>, <weave:> directives. One directive set, one parsing rule, applicable inline or block-level.
each visit { first / then / finally } <cycle> block with arms. Same idea, one keyword.
v2 archetypes (eleven of them) Four: story, module, character, beat. Plus declaration keywords CHARACTER, ITEM, LOCATION, FACTION, ENTITY. The retired archetypes are idioms inside a story, not separate languages.
extends, derives, impls, mixin, template, macro, takes, trait is, plus typed slots with no defaults. Eight forms collapsed to two ideas: composition (is) and abstractness (unfilled slots).
Goals, disposition, hooks, ledger Kept as-is. They were already orthogonal and well-typed.

12. A full example

Six declarations, two beats, one parameterised beat, prompt-book metadata, and a testing anchor. No quotes anywhere. Five bracket shapes, used precisely. 

# The Lighthouse at Dawn
loom: 3
entry: opening
tags: tutorial, single-act

#  Declarations  ─────────────────────────────────

CHARACTER Keeper                       ← abstract; voice has no default
  voice:      any
  home:       any of LOCATION
  reputation: 0 to 100 = 50

CHARACTER Combatant
  hp:     int
  attack: int

CHARACTER Wren is Keeper, Combatant
  voice:      female_alto
  home:       Lighthouse
  reputation: 60
  hp:         80
  attack:     4
  has:        brass_lantern
  knows:      bell_origin

  trusts Player:   30 of 100
  respects Player: 50 of 100

CHARACTER Player is Visitor

ITEM brass_lantern
  weight: 2
  fuel:   75 of 100
  etched: true

LOCATION Lighthouse
  ambient:  wind_low
  contains: bell_rope, brass_lantern

#  Beats  ─────────────────────────────────────────

== opening
  cast: Wren, Player
  setting: Lighthouse

INT. LIGHTHOUSE - DAWN

<<warn lx_dawn>>
<anchor: opening_top>

A bell rope swings in the gloom. Wren watches it from the doorway.

<cue: lx_dawn>

WREN
  (quietly)
  It hasn't rung in three days.
  <<blocking: cross to lantern on "three">>

She turns the lantern up.

* Ring the bell.[ I shouldn't, but I do.]
  -> ring_bell

+ Ask about the keepers.
  -> ask_about with topic: keepers, NPC: Wren

+ Leave quietly.
  -> END

== ring_bell
  cast: Wren, Player
  setting: Lighthouse

<sfx: bell_toll>
<anchor: the_bell_rings>

The sound carries across the rocks.

WREN
  (stunned)
  You... rang it.
  <set: trusts.Player += 20>
  <fire: bell_acknowledged>

<if: Wren.trusts.Player > 40>
  WREN
    Then you should know what I know.
  -> ask_about with topic: bell, NPC: Wren
<else>
  WREN
    Leave. Now.
  -> END

== ask_about(topic)
  cast: NPC, Player
  setting: any

PLAYER
  What can you tell me about {topic}?

<match: NPC.knowledge of topic>
  full
    slot: answer
  partial
    NPC
      I've heard rumours, but nothing I'd swear to.
  unknown
    NPC
      I'm sorry. I don't know.

<<note: consider adding a "rumour" mode that always returns half-truths>>

The caller fills the slot at the divert:

-> ask_about with topic: bell, NPC: Wren
  answer:
    WREN
      The bell rings when the keeper is in danger.
      I was the last keeper before me.
End state. A writer who has read Fountain reads this file as a screenplay. A stage manager reads <<…>> as a prompt-book column. A developer reads <…> as runtime calls. A producer reads declarations as a breakdown. The runtime reads it as a program. One file, five audiences, no overlap.

13. Migration

  1. Two parsers, one runtime. v3 ships behind the header property loom: 3. v2 files (which carry no loom: property or carry loom: 2) keep parsing through the v2 path. Both lower to the shared bundle IR.
  2. v2 desugars to v3 internally. cast SPEAKER becomes a tiny CHARACTER; :conversation becomes a story with an implicit == root knot; ~-prefixed actions become the matching <set:> / <fire:> / <cue:>; {quietly} emotion brackets become (quietly) parentheticals. The IR sees no difference.
  3. Phased rollout. (a) Land v3 grammar behind the flag, shared IR, existing tests green. (b) Port lesson 04 (declaring cast) and lesson 20 (tiny complete story) to v3 as reference. (c) Write the v3-only lessons covering typed slots, is, <<…>> metadata, and the directive set. (d) Soft-deprecate v2 with parser hints. (e) Remove v2 when the examples and the LSP are caught up.
  4. Tooling. The TextMate grammar at tools/loom-syntax/loom.tmLanguage.json gains five bracket scopes — (), {}, [], <…>, <<…>> — each with a distinct theme colour. It loses the three v2 sigil scopes. The LSP gains a directive completion list (kinds enumerated in §8) and a metadata-kind index (so authors can jump between every <<todo:>> in the workspace).

14. Open questions

  • Inline directive density. A heavy dialogue line can carry several <set:> and <sfx:> directives. Do we cap how many fit on one line, or trust the writer? Leaning trust — Ink doesn't cap and writers manage.
  • Knot parameters: parens or takes? == ask_about(topic) reads like a function. An alternative is == ask_about takes topic: text, which is more declarative. Parens win on brevity; takes wins on legibility. Leaning parens — it composes with with topic: bell at the call site.
  • Multi-word string values. label: Wren the Keeper works because the colon takes the rest of the line. But has: brass_lantern, journal, three_candles is a list — what if a list element needs spaces? Leaning toward has: brass lantern, journal, three candles being legal (commas split, leading/trailing whitespace trimmed). If you need a literal comma, use a name token (snake_case) instead.
  • <<…>> first-token registry. Should the kinds inside <<…>> be a closed set the LSP autocompletes (warn, cue, blocking, note, todo, break, related) or open? Leaning open — let production teams invent their own conventions, and have the LSP suggest from the workspace's history.

15. Acknowledgements

Every idea in this document descends from somewhere older. The five-bracket discipline is the only contribution that is genuinely v3. Everything else is recombination — screenplay's positional formatting, Fountain's inference-with-escape, Ink's == / * / + / -> vocabulary and the […] suppress trick, Twine's passage-as-file model, Obsidian/Logseq's local-first identity, and the stage-manager's prompt-book column that v3 lifts into the same file as <<…>>. The weave / loom / thread metaphor predates all of them and is the project's reason for being.
