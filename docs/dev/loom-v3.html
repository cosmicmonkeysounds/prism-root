Loom v3 design

Loom looks like a screenplay. It is not one. Underneath the capitalised speakers and indented dialogue is a non-linear narrative scripting language with reactive bindings, character simulation (Simulacra), stat systems (Meridian), live-theatre participants, improv coroutines, and a tiered scheduler. v3 keeps the screenplay skin — because writers, stage managers, and directors can read it cold — and brings the engine fully back from v2, organised under one bracket discipline.

The three claims.
  1. Screenplay on the outside. Position, capitalisation, and indentation carry meaning. Quotes, apostrophes, and most punctuation belong to the writer. A .loom file printed and handed to a director is directable.
  2. Narrative VM on the inside. The same file is a program — reactive let, hooks that fire on ledger events, character goals as small state machines, generators that drive ambient life, scenes that coordinate multi-step coroutines, factions that hold collective state. Simulacra and Meridian are folded in as first-class declaration kinds, not bolted on.
  3. A project is a folder of .loom files, rooted at main.loom. Beats live wherever they're easiest to write, characters live in their own files, and diverts cross files at will. The runtime resolves names across the whole project, the way Obsidian resolves wiki-links across a vault.

1. Lineage — the formats v3 descends from

Every choice below is borrowed. Knowing which is which is the cheat sheet for the rest of the document.

TraditionWhat v3 takes
Hollywood screenplay (~1920s) Position-is-syntax: ALL CAPS speaker cues, indented dialogue, parenthetical directions in (parens), action lines flush left, scene headings INT./EXT.
Stage prompt book (Samuel French, BBC radio) The parallel cue column. Production metadata sits next to text, not inside it. v3's <<…>> bracket is that column.
Fountain (Maschwitz/August, 2012) Plain-text screenplay with inference and escape. Defaults are positional; sigils only appear when the writer needs to override the inference.
Ink (inkle, 2016 — 80 Days, Heaven's Vault) Knots (==), once-only choices (*), sticky choices (+), diverts (->), gathers (-), tunnels (-> (…) ->), the […] choice-suppress trick, and the mental model of a playhead.
Twine (Klimas, 2009) A passage is both a file unit and a graph node. A beat in v3 lives wherever the writer puts it — its own file, a folder of siblings, or jammed into main.loom.
Obsidian / Logseq (local-first plain-text notes) Identity by filename. Emergent backlinks from bare capitalised names. Inline key: value properties. No YAML frontmatter required.
SolidJS / Reaktiv / S.js (fine-grained reactivity) Reactive let as a live memo. Predicates re-evaluate when their dependencies change, not on a tick. The model behind hooks, goal predicates, and condition-gated dialogue.

v3 contributes one new thing on the surface: the five-bracket discipline (§5). Underneath, it contributes the integration — Simulacra, Meridian, the weave, the live layer, the prompt book, and the multi-file project all share one parser and one ledger.

2. Loom as a format, not a syntax

A syntax requires you to think in tokens, delimiters, escapes. A format is something a human reads and understands without parsing. Markdown is a format. Fountain is a format. v3 is a format with one extra promise: the same file is the writer's screenplay, the stage manager's prompt book, the producer's breakdown, the simulationist's character sheet, and the runtime's program.

Concretely:

  1. Quotes belong to the writer. ", ', «, " never appear in the grammar. A writer can paste any dialogue verbatim and it parses.
  2. Position over delimiters where position works. A name on its own line is a speaker. An indented line under it is dialogue. A paragraph flush-left is action. A line starting with * or + is a choice. These are positional — exactly as screenplay has done for a century.
  3. Brackets, when used, mean one thing each. Five shapes, five distinct jobs, no overlap. §5.
  4. Printable on paper. Anything the runtime alone cares about lives in <<…>> so a producer can mark it as "ignore at the table read."
The skin is not the engine. Loom looks like a screenplay because writers, actors, and directors can read screenplays. But underneath, every .loom file compiles to a node in a reactive graph, a small set of state machines, and a weave of coroutines. The screenplay is a delivery format for a non-linear narrative VM — not a description of it.

3. A Loom project — folders, files, main.loom

A project is a folder. Anywhere in that folder, a file ending in .loom is part of the project. The runtime loads them all, resolves names across them, and starts at main.loom's entry beat.

my-show/ ├── main.loom ← the entry point ├── cast/ │ ├── Wren.loom ← one character per file (optional) │ ├── Player.loom │ └── Bellkeeper.loom ├── locations/ │ ├── Lighthouse.loom │ └── Harbor.loom ├── stats/ │ └── combat.loom ← Meridian: shared stats profile ├── factions/ │ └── KeepersGuild.loom ├── beats/ │ ├── opening.loom │ ├── ringing.loom ← a single beat, on its own │ └── act_two/ │ ├── confrontation.loom │ └── revelation.loom └── generators/ └── HarborChorus.loom ← ambient life

The discipline:

  • main.loom is the entry. Its entry: property names the first beat to play. If entry: is absent, the first == in main.loom wins.
  • The folder tree is for humans, not the resolver. Names are flat across the project; Obsidian/Twine convention. A beat in beats/act_two/revelation.loom is addressable as revelation, or — when disambiguation is needed — as act_two/revelation.
  • Any declaration may live in any file. A character can sit in cast/Wren.loom, or be declared inline at the top of main.loom. The resolver doesn't care; the writer optimises for legibility.
  • Beats can divert into other files. A divert is a -> followed by a beat name. The beat may live anywhere in the project. See §7.
  • Each file declares its own header. loom: 3 sets the parser version; tags: are file-scoped; everything else is project-wide.

4. The imperative weave

Loom is imperative on the outside, reactive on the inside. A beat reads top-to-bottom; the playhead advances through prose, dialogue, cues; branches fork at choices and diverts. Around the playhead, a reactive graph holds derived state (let), predicates (goals, hooks), and live collections (factions, cohorts). When a mutation invalidates a predicate, the affected hooks queue — they do not preempt the playhead. The next time the playhead yields (end of line, end of beat, choice prompt, wait), the scheduler drains the queue.

This is the same execution model as Ink with Solid grafted on. The weave is the branching graph traced by all possible playheads through the document; the reactive graph is the dependency graph among lets, predicates, and stats.

6. The shape of a .loom file

Three zones, mixed freely:

  • Header — a Markdown-style # Title plus key: value properties.
  • Declarations — CHARACTER, ITEM, LOCATION, FACTION, STATS, TREE, GENERATOR, SCENE, COHORT, plus top-level let bindings.
  • Beats — == knot_name followed by a contract (cast:, setting:) and a woven body.

Scene headings (Fountain-style INT. LOCATION - TIME) sit anywhere in a beat body. They tell a director and a reader where they are; they do not define structure — == does that.

7. Diverts across files

A divert is -> followed by a beat reference.

FormMeaning
-> ringing jump to beat ringing, found anywhere in the project
-> Lighthouse/ringing jump to beat ringing, disambiguated by folder path (when two beats share a name)
-> Wren jump to the entry beat of the file declaring Wren (typically a character file with a single beat)
-> ask_about with topic: bell, NPC: Wren parameterised divert — fills slots at the call site
-> (ask_about with topic: bell) -> tunnel call: push continuation, jump, resume on <-
<- return from the current tunnel
-> END terminate the playhead

Cross-file diverts are the heart of the multi-file model. A conversation in main.loom can divert into beats/Lighthouse/ringing.loom mid-line; the playhead doesn't notice the file boundary. Diverts at any indentation level work the same way — inside choices, inside <if:> arms, inside <match:> arms, even inside an indented dialogue block as the line that ends the speaker's turn.

Diverts at any time, from anywhere. A character's dialogue can end with a divert that hands the playhead to a beat in another file. A hook fired by a stat threshold can divert into a reaction beat. A generator can yield a divert. The playhead is a cursor over the whole project, not over one file. 
WREN
  The bell hasn't rung in three days.
  -> Lighthouse/ringing             ← divert ends Wren's turn

* Tell me about the keepers.
  -> cast/Wren#backstory            ← cross-file with explicit knot

* Maybe later.
  -> END

The # form addresses a specific knot inside a target file (used when a file has more than one beat and the divert needs to pick). When omitted, the file's entry beat is the target.

8. Typed slots — the one generic mechanism

Generics in narrative happen at every scale. A merchant beat works for any merchant. A guard character template instantiates any guard. A recognition scene needs a mentor and a mentee. All of these are the same shape: a typed slot, filled at the call site. 

CHARACTER Keeper                       ← abstract: voice has no default
  voice: any
  home:  any of LOCATION
  reputation: 0 to 100 = 50

CHARACTER Wren is Keeper               ← fills the slots, now concrete
  voice: female_alto
  home:  Lighthouse
  reputation: 60

No trait, no abstract. Abstractness is a consequence of unfilled slots. The same mechanism is used for:

WhereLooks likeFilled by
Object propertyvoice: any a child declaration (via is) or instantiation override
Beat cast membercast: NPC, Player the caller, at the divert
Beat parameter== ask_about(topic) the caller (with topic: bell)
Scene parameterSCENE patrol(character, route) the spawn site (spawn patrol with character: Wren, route: harbor)
Iteration variable<for: item in Player.inventory> each pass of the loop

9. Composition: is

One verb. is X, Y pulls in the property declarations of X and Y. Defaults flow into the child unless overridden; required slots must be satisfied or the child stays abstract. 

CHARACTER Humanoid
  hp:    int = 100
  speed: int = 5

CHARACTER Combatant                    ← abstract: hp and attack required
  hp:     int
  attack: int

CHARACTER Bandit is Humanoid, Combatant
  hp:     30                           ← overrides Humanoid.hp; satisfies Combatant.hp
  attack: 8
                                       ← speed inherited from Humanoid (5)

Beats compose the same way; so do stats profiles, scenes, and factions.

10. Simulacra — characters as small simulations

A CHARACTER declaration is the v2 Simulacra package, collapsed into the same syntax as everything else. It carries properties, disposition toward other characters, knowledge, goals, hooks, and generators. None of these need a new bracket; they're indented blocks under the character.

10.1 Disposition

The most-asked-for character depth feature: how does this character feel about that one?

CHARACTER Wren is Keeper
  trusts Player:   30 of 100
  respects Player: 50 of 100
  fears Player:     0 of 100

  reacts trust > 60                          → warm
  reacts fear > 40                           → guarded
  reacts trust < 10 and respect < 30         → hostile

Each X target: N of M line declares a numeric axis bounded 0..M. reacts <cond> → <tag> emits a runtime tag readable in conditions. Mirrors for symmetric relationships: 

  trusts Player: 30 of 100 mirror Player.trusts.Wren

10.2 Knowledge

What this character has learned. A closed schema of typed slots.

CHARACTER Wren
  knows:
    met_player:        bool = false
    bell_origin:       unknown | suspects | confirmed = unknown
    keeper_name:       text?
    rumours:           list of RUMOUR = []
    saw_the_keeper:    bool = false

Mutation surface (only these three):

<set: Wren.knows.bell_origin := suspects>
<set: Wren.knows.rumours += SingingRumour>
<set: Wren.knows.rumours -= SingingRumour>

Knowledge is read-only from outside its character. Every mutation writes a KnowledgeChanged envelope to the ledger; saves round-trip byte-for-byte.

10.3 Goals

What this character is trying to do. Small declarative state machines.

CHARACTER Wren
  goal find_keeper
    priority:       0.8
    active when:    Time.hour > 6 and not Wren.exhausted
    completes when: Wren.knows.saw_the_keeper
    fails when:     Wren.hp < 20
    drives:         search_routine             ← a generator
    on complete:    -> Wren.knows.bell_origin := confirmed
    on fail:        -> log abandoned_find_keeper

Each predicate (active when, completes when, fails when) is reactive — it re-evaluates when its dependencies change, never on a tick. States are dormant → pursuing → (complete | failed); the highest-priority active goal wins. Story can force the machine when it has to: <goal: Wren/find_keeper start>, … complete>, … reset>.

10.4 Hooks — on …

Event-driven character reactions, fired by the ledger.

CHARACTER Wren
  on meeting Player                          ← one-shot encounter
    <if: not Wren.knows.met_player>
      <set: Wren.knows.met_player := true>
      -> introduce_self as Wren

  on trust passes 80                         ← threshold-cross
    -> reveal_secret as Wren

  on Time.hour == 22                         ← in-world clock
    -> retire_for_night as Wren

  on cue bell_strike_loud                    ← crew-bus event
    <set: Wren.knows.heard_the_bell := true>

  on Participant enters Lighthouse           ← location event
    -> greet_visitor as Wren

  on event bell_acknowledged                 ← user-fired event
    <set: Wren.trusts.Player += 10>

The leading clause is matched against the built-in event registry (table identical to v2; the kinds — meeting, passes, drops below, ==, enters, exits, cue, event) carry the same semantics. Edge-triggered predicates fire once per crossing; level-triggered predicates fire once and re-arm only when the predicate becomes false. Hooks never preempt the playhead; they queue and drain at the next yield point.

10.5 Generators on a character

The most direct way to express "what this character does when nobody is talking to them."

CHARACTER Elena
  generator daily_routine
    at 6am   go_to Home
    at 8am   go_to Bakery
    at noon  go_to Harbor

    every random(15m, 45m)
      <if: at Harbor and Weather.fog>
        yield bark from HarborFogChatter

  generator stress_reactions
    when stress > 70
      yield with_chance(0.3)
        ELENA
          (exhausted)
          I need a moment.

A character with no generators is a static prop; one with a few is a village inhabitant; one with a dozen drives an immersive show.

11. Meridian — stats, axes, pools, trees

Stats live on characters or in shared STATS declarations. Five primitives cover every progression model from D&D 5e to Skyrim to Path of Exile, plus "no stats at all" for narrative-only shows. 

STATS Combat
  attribute strength = 10, range 1 to 30
  attribute agility  = 10, range 1 to 30

  axis level
    mode: xp_curve
    curve: level * level * 50
    on advance: <fire: level_up>

  pool health
    max: max_health
    regen: 2/s when not in_combat

  stat max_health = 50 + strength * 5 + Level.lookup(level)
  stat damage     = 8 + strength * 0.5 + (equipped?.bonus or 0)

CHARACTER Wren is Keeper, Combatant
  stats: Combat                              ← include the profile
  strength: 12
PrimitiveMeaning
attributestatic per-character number set at creation
axisdimension that advances at runtime (six modes: xp_curve, use_tracking, point_buy, milestone, narrative_trigger, sdk_controlled)
poolspendable supply with max / regen / cost
statcomputed or tracked value (expression, lookup table, pool, derived)
TREEDAG of unlockable nodes (own declaration kind, often own file)

Trees as their own file:

stats/WarriorPath.loom
TREE WarriorPath
  node armsman_1
    cost:     { skill_points: 1 }
    requires: axis(one_handed) >= 20
    effect:   stat(damage) += 5

  node armsman_2
    cost:     { skill_points: 1 }
    requires: node(armsman_1)
    effect:   stat(damage) += 5
    effect:   ability PowerAttack

Every Meridian primitive is exposed under dot-path on the character: Wren.strength (attribute), Wren.level (axis), Wren.health (pool current), Wren.health.max (pool max), Wren.damage (stat), Wren.tree.armsman_1? (node presence test). The resolver knows which registry owns the name; no bracket prefixes.

12. Reactive bindings: let, hooks, generators, scenes

The functional layer. None of these need a new bracket — they're declarations or directives — but they're the reason Loom is a scripting language and not a markup format.

12.1 Reactive let

A let is a live formula. Its value updates whenever a dependency changes; conditions that read it subscribe automatically. Backed by prism-core::reactive::Memo<T>. 

let trusted    = Wren.trusts.Player > 50
let in_danger  = Player.health < Player.max_health * 0.3
let crowd_size = count(Participants in BellTower)
let allies     = [c for c in Characters where c.faction == Player.faction]
let nearby     = [c for c in Characters where c.distance(Player) < 10]
let hostile    = [c for c in nearby where c.disposition(Player) is hostile]

Conditions are bare names — <if: trusted>. The same form is allowed at any scope: top of file (project-global), inside a beat (beat-local), inside a scene (scene-local).

12.2 Ledger queries

Time and history are expressions. The ledger is one append-only stream; queries are read against per-entity views materialised over it. 

<if: since(bell_rung) < 30s>          ← show-global
<if: since(Participant, bell_rung) < 30s>  ← scoped to one participant
<if: last(Wren, speaker) == Player>       ← Wren's view
<if: visits(opening) == 1>                ← visit counter
<if: played(intro)>                       ← any-time predicate

12.3 Scenes

A SCENE is a labelled coroutine — a multi-step interaction with explicit state transitions. Where a generator yields ambient content, a scene drives a focused exchange. 

SCENE patrol(character, route)
  for waypoint in route
    <goto: character → waypoint>
    wait until character.at(waypoint)
    wait random(3s, 8s)

    <if: character.spotted_intruder>
      -> investigate as character
      return

SCENE investigate(character)
  approach
    <set: character.disposition(Player).suspicion += 5>
    wait until character.at(Player.position)
    -> examine

  examine
    NPC
      (focused)
      Hmm. Something's not right.
    wait random(2s, 4s)
    <if: character.deduction > 60>
      -> confront
    -> withdraw

  confront
    <fire: character.investigated with target: Player, result: clue>
    return clue

  withdraw
    <fire: character.investigated with target: Player, result: none>
    return none

Scenes have parameters, labelled states (the inner bare-name blocks), wait, yield, return. Invoked via spawn patrol with character: Wren, route: harbor (fire-and-forget) or let r = run investigate(character: Wren) (await return value).

12.4 Generators

Long-running coroutines that yield content to the runtime.

GENERATOR HarborChorus
  tier:     ambient
  priority: 0.3

  loop
    wait random(20s, 60s)

    <if: Storm.active>
      DOCKHAND | FISHER
        (worried)
        <shuffle: Storm's close. | Sky's wrong. | Time to tie down.>

    <else if: Bell.ringing>
      VILLAGER
        (surprised)
        The bell! It's ringing!

    <else>
      FISHER | VILLAGER
        <cycle: Quiet night. | Stars are out. | Tide's calm.>

Generators run until cancelled. The runtime starts named generators on boot or via <spawn: HarborChorus>. Multiple generators run concurrently. They are character-bound (declared inside a CHARACTER) or world-bound (top-level).

12.5 Tiered scheduling

Round-robin breaks at scale. Every generator and scene runs in one of three tiers:

TierWhen it ticksDefault population
focalevery frameactive conversation; scenes the camera/PoV is in
activeevery ~100msnearby NPCs; characters the player has spoken with recently
ambientevery ~2sdistant NPCs; world generators; village background

Each tier has a per-tick budget. Author override is always explicit on the declaration (tier:, priority:). A scene marked tier: focal is never deferred — the scheduler steals from active and ambient before dropping a focal frame.

13. Live performance — participants, cohorts, improv, broadcasts

Live immersive theatre is what falls out of the rest of the language when participants are first-class. The pieces here are all that's needed; cast, story, stats, hooks all work the same on stage as on a controller.

13.1 Participants & cohorts

COHORT Initiates
  label:    The Initiates
  capacity: 24

LOCATION BellTower
  label:    The Bell Tower
  capacity: 12

on participant joins
  <enroll: Participant → Initiates>
  -> orientation as Participant

on participant enters BellTower
  -> bell_first_visit as Participant

The as Participant modifier scopes a beat to one audience member — inside such a beat, trust resolves to Participant.trust, not a show-global. Many participants can play the same beat simultaneously without interfering.

13.2 Broadcast scopes

<broadcast: participant(Participant)>
  NARRATOR
    (whispering)
    You hear it differently. You always have.

<broadcast: location(BellTower) but participant(Participant)>
  NARRATOR
    The others look up.

<broadcast: cohort(Singers) and location(BellTower)>
  <cue: private_choir>

Scope atoms compose with and (intersection) and but (difference). The runtime applies the filter to the broadcast's content stream.

13.3 Improv with pluggable advancement

BELLKEEPER
  (improv duration: 45s, advance on: any [pedal, speech(anchor phrase), gesture(Bow)])
  (Greet warmly. Find out why they came. Don't reveal the singing —
   that's act two.)

  -> next_beat

The parenthetical body is a directive to the performer (the parens keep it out of the spoken line). The runtime displays it on the performer's prompter, holds the playhead until any configured signal arrives or duration elapses, and writes ImprovBeatStarted / Advanced envelopes to the ledger. Quorum operators (all, any, quorum(N)) match v2.

13.4 Live patching from the booth

The booth UI — a Prism app on the same LoomRuntime — can skip a participant past a beat, force-fire a cue, re-cast a role, retire a participant who left, hot-reload a .loom patch without stopping the show. Every booth action is a Loro CRDT op on the same store. The booth is just another client.

14. Runtime directives — <…>

Every directive is <kind: args> (or <kind> for nullary). Block-opening directives have an indented body and end at dedent.

sfx<sfx: bell-toll>fire a sound effect

fire<fire: bell_acknowledged>fire a named event onto the bus

Anchors are first-class. <anchor: name> is the v3 testing primitive. Tests jump to anchors, analytics count how many players reach them, links cross-reference them, the authoring tool's "skip to here" affordance uses them. Lift anchors liberally — they're cheap.

15. Production metadata — <<…>>

The prompt-book column, lifted inline. The runtime parses it and does nothing at production. It exists for stage managers, producers, authors, and debuggers. The first token names the kind; tooling filters on it. 

<<warn lx14>>
<<warn sq7>>

WREN
  (quietly)
  It hasn't rung in three days.
  <<blocking: cross DSR on "rang">>

<<lx14 go>>
<<sq7 go on "Mitch">>

<<note: this scene felt long at the table read — try cutting the lantern beat>>
<<todo: confirm with director that the silence after the bell holds>>
<<break: trust >= 80>>     ← debugger conditional breakpoint
<<related: Wren/backstory>>

16. Worked example: a small project across files

A five-file project. One main.loom, one character file, one location file, one stats profile, one scene. Cross-file diverts, a reactive let, a hook, a generator, and an improv beat. 

main.loom
# Saltmere
loom: 3
entry: opening

let trusted = Wren.trusts.Player > 50

== opening
  cast: Wren, Player

17. Migration from v2

  1. Two parsers, one runtime. v3 ships behind the header property loom: 3. v2 files (no loom: or loom: 2) keep parsing through the v2 path. Both lower to the shared bundle IR.
  2. v2 desugars to v3 internally. cast SPEAKER becomes a tiny CHARACTER; :conversation becomes a file with an implicit == root; ~-prefixed actions become the matching <set:> / <fire:> / <cue:>; {quietly} emotion brackets become (quietly) parentheticals; $x becomes bare x under lexical resolution; @x/[[x]] become bare capitalised names. The Simulacra and Meridian semantics carry over unchanged — the names change shape, not the model.
  3. Phased rollout. (a) Land v3 grammar behind the flag, shared IR, existing tests green. (b) Port lessons 04 (declaring cast) and 20 (tiny story) to v3 as reference. (c) Add v3-only lessons for typed slots, multi-file projects, the reactive layer, the live layer. (d) Soft-deprecate v2 with parser hints. (e) Remove v2 when examples and the LSP have caught up.
  4. Tooling. The TextMate grammar at tools/loom-syntax/loom.tmLanguage.json gains five bracket scopes — (), {}, [], <…>, <<…>> — and a cross-file divert resolver in the LSP. The LSP gains project-aware name completion (every CHARACTER, every beat, every anchor, every <<todo:>> in the workspace).

18. Open questions

  • Divert ambiguity resolution. When two beats in different files share a name, do we error and force the writer to qualify (Lighthouse/ringing), or pick by some heuristic (closest in the folder tree, most-recently-touched)? Leaning error — silent guessing is the worst failure mode for narrative tools.
  • File-level cast: shorthand. Should a file declare a default cast that all its beats inherit, so the per-beat cast: can be omitted? Leans yes for character-centric files (cast/Wren.loom); leans no for hub files. Probably both, with an explicit per-beat override.
  • Hot-reload granularity. Editing cast/Wren.loom mid-show — do all in-flight hooks finish under the old definition, or rebind at the next ledger flush? v2 chose "finish under the old"; keeping that is the safer default but worth re-confirming with live operators.
  • Reactive let visibility across files. A let in main.loom is project-global by default. Should files be able to declare lets that are file-local (not visible to other files)? Leaning yes via a local let form, but the common case is the global one.

19. Acknowledgements

Every idea here descends from somewhere older. The five-bracket discipline and the multi-file project model are v3's only contributions. Everything else is recombination — screenplay's positional formatting, Fountain's inference-with-escape, Ink's == / * / + / -> vocabulary and the […] suppress trick, Twine's passage-as-file model, Obsidian/Logseq's local-first identity, fine- grained reactivity from the Solid/S.js lineage, the prompt-book column from a hundred years of stage management, and the character / stat / faction model that v2 built as Simulacra and Meridian. The weave / loom / thread metaphor predates all of them and is the project's reason for being.
