Loom — a friendly reference

Loom is a way to write stories that branch, react, and come to life — but it reads like a screenplay. This guide assumes nothing. By the end you'll be writing simple branching scenes, characters with feelings and memory, immersive theatre that addresses each audience member by name, and ambient worlds that hum along on their own.

How to read this guide. The first half is a tutorial — work through it in order. The second half is reference — flip in, look something up, flip out. The badges next to each section header tell you the level: beginner intermediate advanced. If you skip ahead and feel lost, the earlier sections probably hold the missing piece.

1. What is Loom? beginner

Loom is a small language for writing branching stories. It is designed for people who write — novelists, playwrights, game designers, immersive-theatre directors, audio dramatists. You don't need to be a programmer to use it. You write something that looks like a screenplay, and a computer turns it into a working story.

The same file can be:

  • A screenplay a writer hands to a director.
  • A prompt book a stage manager runs a show from.
  • A game script a player explores by making choices.
  • A live-theatre cue sheet driving lighting, sound, and audience-specific moments.
  • A character sheet with feelings, knowledge, and goals that change as the story plays out.

None of those are "modes". They are all the same file, read by different audiences. The trick is a small, consistent grammar that lets each audience ignore the parts they don't need.

The promise. If you can write a paragraph of dialogue with a name on top, you can write Loom. Everything else — variables, branching, characters with memory, live audiences — is added one small idea at a time.

2. Screenplay 101 — speakers, dialogue, action beginner

If you've never written a screenplay before, the format takes about three minutes to learn. Loom uses the same rules, plus a few additions you'll meet later. The conventions are positional — where something is on the page is what tells the runtime (or a reader) what it is.

The four shapes you'll see

Action line
A paragraph flush to the left margin. It describes what happens, in present tense.
Speaker
A name in ALL CAPS on its own line. It says who is talking next.
Dialogue
The lines indented under a speaker. The actual words spoken.
Parenthetical
A note in (parentheses) indented above or inside dialogue. A direction for the performer — tone, action, blocking.

That's the whole format. Here it is in one example:

INT. LIGHTHOUSE - DAWN

A bell rope swings in the gloom.

WREN
  (quietly)
  It hasn't rung in three days.

She turns the lantern up.

WREN
  Whoever you are — listen.

Let's walk through it:

  • INT. LIGHTHOUSE - DAWN is a scene heading. INT. means interior; the rest names the place and time. The runtime ignores it. It exists for the reader.
  • A bell rope swings in the gloom. is an action line. Flush left, written in present tense, describes the world.
  • WREN in ALL CAPS is a speaker cue. Wren is about to speak.
  • (quietly) is a parenthetical. It tells the performer how to deliver the next line.
  • It hasn't rung in three days. indented under Wren is her dialogue.
The screenplay trick. ALL-CAPS-on-its-own-line means "someone is about to speak." Indented-under-a-speaker means "this is what they say." Flush-left-paragraph means "this is what's happening in the world." You do not need any other markers. Loom adds a handful of brackets on top of this skeleton, but the screenplay rules stay intact.

Multiple speakers in one breath

If two or more characters speak in unison, put both names on the speaker line, separated by |:

WREN | FISHER
  (stunned)
  You... rang it.

This matters most in live performance — the runtime sends the line to both performers.

3. Your first .loom file beginner

A Loom story lives in a file with a .loom extension. The smallest possible useful file looks like this: 

# Hello
entry: opening

== opening

INT. ROOM - DAY

A first sentence appears on the page.

NARRATOR
  Welcome to Loom.

-> END

Three things you've just done:

  1. Given your story a title (# Hello) and named the starting beat (entry: opening).
  2. Declared a beat called opening with == opening. A beat is a named scene the runtime can jump to.
  3. Ended the playhead with -> END. The arrow -> means "jump to," and END is a built-in target that stops the story.

Save that as main.loom, point Loom at it, and the runtime will print the action line, deliver the narrator's line to a voice, and stop. You have made a tiny story.

Why main.loom? Loom always starts at a file named main.loom in the project folder. Every other file is optional. We'll cover multi-file projects in §28 — for now, one file is plenty.

4. The header at the top beginner

At the top of main.loom you write a small header. It looks like the front matter you'd see in a markdown document or an essay. 

# Saltmere
entry: opening
tags:  tutorial, lighthouse
author: Jane Writer
LineWhat it does
# TitleThe story's title. One line, starts with a single #.
entry:The name of the beat to start in. If you skip this, Loom starts at the first == in the file.
tags:Comma-separated tags for organising. Loom doesn't enforce a meaning; tools can filter by them.
author: / title: / next:Optional metadata. Free-form, for tools that want to read it.

None of these are mandatory. You can write a working Loom file with no header at all — just an opening beat and some content.

5. Beats — splitting your story into named scenes beginner

A beat is a named chunk of your story. The runtime can jump from one beat to another. They are how a non-linear story is built up: instead of one long file, you write little pieces and connect them.

You declare a beat with two equals signs and a name:

== opening
  cast: Wren, Player
  setting: Lighthouse

INT. LIGHTHOUSE - DAWN

A bell rope swings in the gloom.

The lines immediately after == opening are the beat's contract:

cast:
Who is in this scene. Lets tools warn you if you start writing dialogue for someone who isn't present.
setting:
Where this scene takes place. Plain text or a named LOCATION (covered later).
with topic:
For beats that take parameters — see typed slots.

Below the contract is the body: action lines, dialogue, choices, anything else.

Why two equals signs? Loom borrows == from Ink (a sister narrative language). It's visually distinct, easy to scan for, and impossible to confuse with markdown headings. Think of it as "this is a beat marker."

6. Choices — * and + beginner

A choice is a moment where the reader (or player) picks what happens next. Choices look like this: 

WREN
  (quietly)
  It hasn't rung in three days.

* Ring the bell.
  -> ringing
* Leave quietly.
  -> END

Each line starting with * is a choice. The text after * is the label the reader sees. The indented lines under it are what happens if they pick that option.

There are two kinds of choice marker:

MarkerBehaviorWhen to use
* Once-only. Disappears after the reader picks it. Branching decisions; one-time actions.
+ Sticky. Stays available every time the reader sees this beat. "Ask about…" menus, recurring options, anything the reader can do repeatedly. 
+ Ask about the bell.
  -> ask_bell
+ Ask about the keepers.
  -> ask_keepers
* Leave.
  -> END

Here the reader can ask about the bell and the keepers as many times as they want, but once they leave, the leave option is gone.

7. Diverts — jumping between beats beginner

A divert is the arrow -> followed by a beat name. It tells the playhead "go there next." 

-> ringing            ← jump to the beat called "ringing"
-> END                ← stop the story
-> Lighthouse/dawn    ← jump to a beat in a specific folder (when needed)

Diverts can appear almost anywhere in a beat:

  • At the end of a beat (the most common spot).
  • At the end of a choice's body.
  • Inside an <if:> branch.
  • Even at the end of a character's dialogue.
WREN
  Then you should know what I know.
  -> ask_about

Here, the divert ends Wren's turn — once she finishes speaking, the playhead jumps to the ask_about beat. Diverts are the primary way a non-linear story moves.

Built-in target: END

-> END is the one reserved divert target. It tells the playhead to stop. Every "ending" in your story is reached by a -> END somewhere.

Diverts with parameters

A beat can take parameters — we'll cover this more in §25, but the surface form is worth seeing now: 

== ask_about(topic)
  cast: NPC, Player

PLAYER
  Tell me about the {topic}.

And the caller fills topic at the divert site:

* Ask about the bell.
  -> ask_about with topic: bell

The {topic} inside the beat will be replaced with bell at runtime. This is how you write one beat that handles many similar conversations.

Tunnels — go somewhere, come back

Sometimes you want the playhead to detour into another beat and then return to where it left off. That's a tunnel: 

-> (cleanup) ->    ← jump into cleanup, then come back
                    (the next line continues here)

And inside cleanup, the tunnel returns with:

<-

Tunnels are useful when several beats need to share a piece of logic (reset some state, play a recurring cue, do a quick check). For your first stories you'll rarely need them.

8. The […] suppression trick beginner

Square brackets do one specific job borrowed from Ink: they let a choice label and the narration that plays after the choice differ. 

* "Yes."[ I said firmly.]
  -> agreed

This produces:

  • The button the reader sees: "Yes."
  • The line that plays after they click: "Yes." I said firmly.

Anything inside […] appears in the spoken narration only, not in the button. It's how you keep choice labels short while keeping the prose natural.

9. The five brackets, one job each beginner

Loom uses five kinds of brackets, and each one does exactly one thing. This is the most important table in the whole document — if you remember it, the rest of Loom is just vocabulary.

Bracket Who it talks to What it does Example
( … ) the performer direction — how to act or read (quietly)
{ … } the reader insert a value into text Hello, {Player.name}.
[ … ] the reader (hidden from choice) suppress text from the choice label "Yes."[ I said firmly.]
< … > the runtime do something — play a sound, set a value, branch <sfx: bell>
``` … ``` the production team notes for stage managers, producers, editors ```warn lx14```
The cheat. When you're not sure which bracket to use, ask "who is this for?" If it's the actor — parentheses. If it's a value the reader should see — curly braces. If it's an instruction the computer carries out — angle brackets. If it's a note for the lighting designer — triple backticks. Once you've got that down, you've got Loom.

10. Parentheses — directions for the performer beginner

Anything inside ( … ) is a direction. It belongs to the actor or narrator delivering the line. It is not spoken aloud. 

WREN
  (whispering, almost to herself)
  It hasn't rung in three days.

She moves to the window. (slow — the storm is just starting)

Common uses:

  • Tone: (quietly), (furious), (unsure)
  • Action: (she crosses to the door)
  • Beat / pause: (beat), (pause)
  • Improv instruction (special): see §22

11. Curly braces — values mixed into text beginner

Curly braces { … } let you drop a value into a line. Anywhere you put {expression} inside an action line or dialogue, Loom replaces it with the current value. 

NARRATOR
  You have {coins} coins and {keys} keys.

WREN
  Welcome back, {Player.name}.

This is sometimes called interpolation. The braces are essentially "paste this value here."

12. Angle brackets — telling the runtime to do something beginner

Angle brackets < … > are how you tell the runtime to do something. Play a sound. Change a value. Check a condition. These are sometimes called directives. 

<sfx: bell_toll>                 ← play a sound effect
<cue: lx14>                      ← fire a named cue
<set: Wren.trusts.Player += 10>  ← change a value
<pause: 2s>                      ← wait two seconds
<anchor: opening_top>            ← name this position

The first word after < is the directive name. The colon separates the name from its arguments. Arguments can be positional (separated by commas) or named (using key: value).

Some directives also open blocks — they contain other lines, indented underneath: 

<if: Wren.trusts.Player > 50>
  WREN
    I knew you'd come.

We'll cover the most common directives in the next part. There are dozens more in the directives table at the back.

13. Triple backticks — production notes beginner

A triple-backtick fence ``` … ``` is a region the runtime ignores. It's for everyone else who reads the script: stage managers, lighting designers, sound designers, producers, future you. 

```warn lx14```            ← inline form: one line

```note
This scene felt long at the table read. Try cutting the lantern beat;
the silence after the bell carries more than the dialogue.
```                        ← block form: multiple lines

The first word inside the fence is the kind of note. Useful kinds:

TagMeaning
noteGeneral-purpose note.
warnHeads-up for the operator (a cue is coming).
cueA named cue point.
blockingStage direction for blocking.
todoSomething to fix later — tools surface these.
breakA debugger breakpoint (advanced).
relatedCross-reference to another beat.

You can invent new tags freely. Tools that don't recognise a tag treat it as a note.

14. Comments — notes only the writer sees beginner

If a triple-backtick fence is for the production team, a comment is for the next writer (often future you). Comments don't appear in the script at runtime or in any production view.

Loom borrows C-style comments:

// rough order: bell, beat, lantern up, line
WREN
  (quietly)
  It hasn't rung in three days. // pickup pace if Wren's actor is fast

/*
  blocking sketch from rehearsal 04-12:
  Wren is upstage left at the rope. Player enters from SR on the bell.
*/
FormScope
// …To the end of the line.
/* … */Across as many lines as you want.
One small rule. // must be at the start of a line, or have whitespace before it. This is so URLs in dialogue (https://example.com) don't accidentally become comments.

15. Variables with let intermediate

A variable is a name that holds a value. In Loom, you declare variables with let: 

let trusted    = Wren.trusts.Player > 50
let in_danger  = Player.health < 30
let crowd_size = count(Participants in BellTower)

Each let binds a name to an expression. The crucial trick is that the value updates automatically as its inputs change. If Wren's trust climbs above 50, trusted becomes true with no further action from you. If the player heals, in_danger turns false on its own.

This is called reactive — Loom watches the inputs for you.

You then use the name as a condition:

<if: trusted>
  WREN
    I knew you'd come.
Why this is nice. You don't have to remember to update trusted every time Wren's trust changes. The name is a live formula, not a snapshot. Most of your conditions will read better when you name them this way once at the top of the file.

Top-level vs beat-local let

A let at the top of a file is visible everywhere in your project.

# Saltmere
entry: opening
let trusted = Wren.trusts.Player > 50    ← visible to every beat

A let directive inside a beat is local to that beat:

== ringing
  cast: Wren, Player

<let: bell_count = visits(ringing)>       ← local to this beat
<if: bell_count > 3>
  NARRATOR
    The bell is wearing thin.

16. Changing values with <set:> intermediate

<set:> is the directive that mutates the world. Anything you want to remember happened — a stat going up, a flag being set, a knowledge fact learned — flows through <set:>. 

<set: Wren.trusts.Player += 10>          ← bump trust by 10
<set: Wren.knows.bell_origin := suspects>  ← change knowledge
<set: Wren.knows.rumours += SingingRumour> ← add to a list
<set: Wren.knows.rumours -= SingingRumour> ← remove from a list
<set: Wren.hp := 80>                     ← assign directly
OperatorWhat it does
:=Replace the value.
+=Add to a number, or append to a list.
-=Subtract from a number, or remove from a list.

Every <set:> writes an entry to the runtime's ledger. The ledger is the story's permanent record — it's how saves work, how hooks fire, and how queries like visits(opening) and since(bell_rung) get answered.

17. Conditionals — <if:>, <else if:>, <else> intermediate

The most common branch you'll write. The body indented under the directive runs only if the condition is true. 

<if: Wren.trusts.Player > 80>
  WREN
    Then you should know what I know.
  -> reveal

<else if: Wren.trusts.Player > 40>
  WREN
    Maybe. Not yet.

<else>
  WREN
    Leave. Now.
  -> END

The chain reads exactly as English does: if A, else if B, else C.

Conditions can be:

  • Comparisons: >, <, ==, !=, >=, <=
  • Booleans (plain true/false): Wren.knows.met_player
  • Combinations with and, or, not
  • A named let: <if: trusted>
  • A ledger query: <if: visits(opening) > 2>

18. Putting values into dialogue intermediate

You met this earlier under curly braces. The full power:

NARRATOR
  Welcome, {Player.name}. You have {Player.coins} coins.

NARRATOR
  Wren {Wren.knows.met_player ? "smiles" : "stares"} at you.

WREN
  I owe you {damage_taken * 2} silver for what you did.

Anything inside {…} is evaluated, the result converted to text, and pasted into the line. You can do arithmetic, look up properties, even branch with a condition ? yes : no expression.

19. Picking arms with <match:> intermediate

Sometimes you want to switch on a value with more than two options. <match:> dispatches to the first arm whose label matches. 

<match: weather>
  storm
    NARRATOR
      Rain hammers the roof.
  fog
    NARRATOR
      The lighthouse beam is the only thing moving.
  clear
    NARRATOR
      Stars over the harbour.

Each indented label (storm, fog, clear) is an arm. The arm whose label equals the value of weather runs. If none match, nothing runs.

<match:> is especially handy for knowledge fields with a fixed set of states: 

<match: NPC.knows.bell_origin>
  confirmed
    NPC
      The bell calls when the keeper is in danger.
  suspects
    NPC
      I've heard rumours, but nothing I'd swear to.
  unknown
    NPC
      I'm sorry. I don't know.

20. Differing each visit intermediate

<each visit> picks a different arm depending on how many times the playhead has reached this beat. It has three arms: 

== bell_tower
  cast: Wren, Player

<each visit>
  first
    NARRATOR
      The bell tower is dark. Your eyes adjust.
  then
    NARRATOR
      The tower is familiar now.
  finally
    NARRATOR
      You've been here too many times. The dust knows you.

first runs on visit 1, then on visit 2, and finally on every visit from 3 onward. This is a clean way to make a beat feel different on subsequent visits without writing three separate beats.

21. Latching with <after:> / <otherwise> intermediate

<after: condition> is "once this becomes true, switch permanently." Before it switches, <otherwise> runs. 

<after: Wren.knows.bell_origin == confirmed>
  WREN
    We don't speak of the bell here.
<otherwise>
  WREN
    Welcome to the lighthouse.

This is a one-way latch: once Wren knows the bell's origin, this beat uses the <after:> body forever, even if her knowledge somehow reverted. (Edge case: knowledge usually only moves forward.)

22. Variation — <shuffle:> and <cycle:> intermediate

Two small directives that add variation to ambient lines.

DirectiveBehavior
<shuffle: a | b | c> Picks one of the options at random. Different (well, pseudo-random) each time the line is reached.
<cycle: a | b | c> Returns the options in order, looping back to the start. 
FISHER
  <shuffle: Storm's close. | Sky's wrong. | Time to tie down.>

VILLAGER
  <cycle: Morning. | Afternoon. | Evening. | Night.>

Use shuffle for crowd chatter that should feel random; use cycle for a sequence you want to play through in order (e.g. a series of escalating threats).

23. Remembering what happened — the ledger intermediate

Every change in your story — every <set:>, every beat visit, every cue, every choice — gets recorded in the ledger. The ledger is the story's memory. You can ask it questions inside conditions.

QueryWhat it returns
visits(opening)How many times the playhead has entered opening.
played(opening)true if opening has ever played.
since(bell_rung)Time elapsed (in seconds) since the named anchor or set fired.
since(Participant, bell_rung)Same, but scoped to one participant (live performance).
last(Wren, speaker)Who Wren last spoke to.
<if: visits(opening) > 3>
  NARRATOR
    You've been here a while. Things have shifted.

<if: since(bell_rung) < 30s>
  WREN
    The bell. Still resonant.

<if: played(reveal_secret)>
  WREN
    You know now. There's no unknowing.

Anchors — naming places in the story

An anchor is a named position in your story. You drop one with the <anchor:> directive: 

<anchor: bell_rung>

Now you can ask "how long since bell_rung happened?" with since(bell_rung), or test if you've crossed it with played(bell_rung). Anchors are cheap — sprinkle them liberally wherever you might want to refer back.

24. Declaring a CHARACTER intermediate

So far our characters have been names that show up to speak. A CHARACTER declaration gives them substance: properties, feelings, memories, goals, behaviours. 

CHARACTER Wren
  voice:      female_alto
  home:       Lighthouse
  reputation: 60
  hp:         80

That's the simplest form: a name, then indented key: value lines underneath. Any name you put on the left of the colon becomes a property of the character. Now Wren.voice, Wren.home, and Wren.hp all exist and can be read or set anywhere in your project.

25. Disposition — trust, respect, fear intermediate

Characters can have feelings about each other. Loom gives you a built-in shape for this: 

CHARACTER Wren
  trusts Player:   30 of 100
  respects Player: 50 of 100
  fears Player:     0 of 100

  reacts trust > 60                       → warm
  reacts fear > 40                        → guarded
  reacts trust < 10 and respect < 30      → hostile

Each X target: N of M line declares a numbered axis between 0 and M, starting at N. Common verbs are trusts, respects, and fears, but you can invent your own.

The reacts lines emit a tag when the condition becomes true. Other conditions can read these tags: 

<if: Wren.is.warm>
  WREN
    Come in, come in. Sit.

Mirrors

If trust runs both ways, you can mirror it:

  trusts Player: 30 of 100 mirror Player.trusts.Wren

Now any change to Wren.trusts.Player is also visible on Player.trusts.Wren (and vice versa) — useful for relationships where the math should stay symmetric.

26. Knowledge — what a character has learned intermediate

Disposition is "how do they feel." Knowledge is "what do they know." 

CHARACTER Wren
  knows:
    met_player:     bool = false
    bell_origin:    unknown | suspects | confirmed = unknown
    keeper_name:    text?
    rumours:        list of RUMOUR = []
    saw_the_keeper: bool = false

Each line in the knows: block declares a typed slot:

TypeMeans
booltrue or false.
int / numberWhole or decimal number.
textA string. text? means optional (can be unset).
A | B | COne of a fixed set of named values.
list of TAn ordered list of things of type T.
map of K to VA mapping from K to V.
range A to B = NA number between A and B, starting at N.

You change knowledge with the usual <set:>:

<set: Wren.knows.met_player := true>
<set: Wren.knows.bell_origin := suspects>
<set: Wren.knows.rumours += SingingRumour>

Knowledge is read-only from outside the character: you can only change Wren's knowledge with a Wren.knows.* set. This makes it easy to track who learned what.

27. Goals — what a character is trying to do advanced

A goal is a small state machine on a character. It has predicates that say when it's active, when it's complete, and when it's failed. 

CHARACTER Wren
  goal find_keeper
    priority:       0.8
    active when:    Time.hour > 6 and not Wren.exhausted
    completes when: Wren.knows.saw_the_keeper
    fails when:     Wren.hp < 20
    drives:         search_routine          ← a generator
    on complete:    <set: Wren.knows.bell_origin := confirmed>
    on fail:        -> abandoned_quest

What each line does:

priority:
Higher-priority goals win when more than one is active.
active when:
The condition that makes the goal eligible. Re-evaluates automatically as inputs change.
completes when:
The condition that means the goal succeeded.
fails when:
The condition that means it failed.
drives:
A generator that runs while this goal is active. (See §32.)
on complete: / on fail:
What to do when the goal resolves.

28. Hooks — characters reacting to events intermediate

A hook is "when X happens, do Y." You write hooks inside a CHARACTER body, leading with on …. 

CHARACTER Wren
  on meeting Player
    <if: not Wren.knows.met_player>
      <set: Wren.knows.met_player := true>
      -> introduce_self as Wren

  on trust passes 80
    -> reveal_secret as Wren

  on Time.hour == 22
    -> retire_for_night as Wren

  on cue bell_strike_loud
    <set: Wren.knows.heard_the_bell := true>

  on Participant enters Lighthouse
    -> greet_visitor as Wren

  on event bell_acknowledged
    <set: Wren.trusts.Player += 10>

Hook event kinds:

FormFires when…
on meeting XThis character first encounters X (once per pair).
on trust passes N / respect passes NThe named axis crosses N going up.
on trust drops below NThe axis crosses N going down.
on Time.hour == 22The in-world clock reaches a value.
on Participant enters XAn audience participant enters location X.
on Participant exits XAn audience participant leaves X.
on participant joinsA new audience participant joins the show.
on cue XThe named cue fires (often from the booth).
on event XA user-fired event named X (via <fire: X>).
Hooks never interrupt. If a hook fires while the playhead is in the middle of a line, the hook waits — it runs at the next "yield" point (end of a line, end of a beat, a choice prompt, a wait). You'll never get a hook talking over an actor.

29. Reusing with TRAIT advanced

When two characters share behaviour — say, every guard patrols, every shopkeeper haggles — you don't want to repeat yourself. A trait is a reusable bundle of properties, hooks, generators, and goals. 

TRAIT Patrolling
  route: list of LOCATION                    ← required slot; no default

  generator walk_route
    tier: ambient
    loop
      for waypoint in route
        <goto: self → waypoint>
        wait until at(waypoint)
        wait random(4s, 10s)

  on cue alarm
    <goto: self → route.first>

You mix the trait into a character with is:

CHARACTER Guard is Humanoid, Combatant, Patrolling
  hp:     80
  attack: 6
  route:  [Gate, Wall, Courtyard]

Now Guard has everything Patrolling defines — the route property, the walk generator, the alarm hook — without you re-writing any of it.

A character can mix in any number of traits:

CHARACTER Goblin is Humanoid, Combatant, Looter, Talkative
  hp: 20

30. Inheritance, traits, and composition advanced

Loom gives you three ways to share behaviour. They look similar; the difference is conceptual.

MechanismRelationshipUse when…
Inheritance is-a A specific kind of an existing thing. GoblinKing is Goblin — a king is a kind of goblin.
Trait mixing can-do A capability bundle. Goblin is Looter — a goblin can be looted.
Composition has-a A property that points to another thing. loot: LootBag = goblin_pouch.

All three coexist. A typical character uses all three at once: it inherits its base type (is Humanoid), mixes in capabilities (Looter, Patrolling), and composes properties by reference (loot: LootBag = goblin_pouch).

31. Overrides and super advanced

Every property and hook in a parent has a name. A child that declares the same name replaces the parent's version. 

CHARACTER ChattyGuard is Guard
  chattiness: 90               ← overrides Guard.chattiness

To extend the parent rather than replace it, call super:

CHARACTER ChattyGuard is Guard
  on meeting Player
    super                       ← run the parent's hook first
    GUARD
      And try not to drip on the flagstones.

To suppress an inherited hook entirely:

CHARACTER QuietGuard is Guard
  on meeting Player: none

Constructors, self, and methods

Every declaration in Loom is a class. That sounds heavy, but in practice it shows up in three small pieces you only need when you reach for them:

  • init — a constructor body. Runs when the declaration is instantiated. Receives named args from the call site.
  • self — the instance under construction or under call. self.strength is the instance's own strength; self.owner on an embedded profile is the character it's embedded in.
  • method — a callable on the instance. method swing(target) declares Wren.swing(Goblin).
STATS Combat
  attribute strength = 10
  init(strength: int? = none)
    if strength is not none
      self.strength = strength
  stat damage = 8 + self.strength * 0.5
  method swing(target)
    target.health -= self.damage

You can ignore all three when you don't need them — a declaration with no init just lets every property default. The moment you write stats: Combat(strength: 12), you are calling that synthesised init.

32. Stats with STATS advanced

Some stories have numbers — health, mana, attack, level. Loom's stat system is called Meridian, and it covers nearly every progression model with five primitives.

You declare a stats profile once, then include it in a character:

STATS Combat
  attribute strength = 10, range 1 to 30

  axis level
    mode: xp_curve
    curve: level * level * 50

  pool health
    max: self.max_health
    regen: 2/s when not self.in_combat

  stat max_health = 50 + self.strength * 5
  stat damage     = 8 + self.strength * 0.5

  method swing(target)
    let blow = self.damage + d6()
    target.health -= blow
    return blow

And include it like this:

CHARACTER Wren is Keeper, Combatant
  stats: Combat(strength: 12)

strength: 12 is not a property bolted onto Wren — it's an argument to Combat's constructor. Wren.stats is a Combat instance that owns the value; self inside the STATS body always refers to that instance.

You'll see two shorter forms for the same call — they all mean the same thing: 

stats: Combat(strength: 12)        ← canonical, what the runtime sees

stats: Combat                      ← indented block: tidy in tutorials
  strength: 12

stats.strength: 12                 ← dotted: one-line override

Reading is even friendlier. Wren.strength is a shortcut for Wren.stats.strength, and so are Wren.health, Wren.damage, Wren.swing(Goblin) — Loom folds any unambiguous embedded-profile name onto the character so authors can write what they mean. Writes are stricter: <set:> always names the canonical path (Wren.stats.strength) so the owner of mutable state is never in doubt.

33. Attributes, axes, pools, stats advanced

PrimitiveWhat it isExample
attribute A static number set at creation, optionally clamped. attribute strength = 10, range 1 to 30
axis A dimension that advances at runtime (e.g. level). axis level
  mode: xp_curve
  curve: level * level * 50
pool A spendable supply with a max and a regen rule. pool health
  max: max_health
  regen: 2/s when not in_combat
stat A computed value — an expression of other stats and attributes. stat damage = 8 + strength * 0.5

Axes can advance in six modes:

xp_curve
Classic experience curve — accumulate XP, level up at thresholds.
use_tracking
Skill goes up by being used (Skyrim style).
point_buy
Player spends points (D&D style).
milestone
Advance at scripted moments.
narrative_trigger
Advance when a story condition is met.
sdk_controlled
External code decides.

34. Skill trees with TREE advanced

A TREE is a directed graph of unlockable nodes — a skill tree, a talent tree, a tech tree. 

TREE WarriorPath
  node armsman_1
    cost:   1
    effect: stat(damage) += 5

  node armsman_2
    cost:     1
    requires: node(armsman_1)
    effect:   stat(damage) += 5

Each node can declare a cost, a requires gate (referring to other nodes or axes), and one or more effect lines. The runtime tracks which nodes a character has taken and gates progression accordingly.

35. Roles, people, rosters, cast advanced

Loom drives immersive live shows. The trick to writing one is to keep the fictional character and the real person playing them as separate things you can rebind on the fly. Four nouns cover it:

NounWhat it is
ROLE A scripted character — Wren, the Bellkeeper, the Initiate. The fiction. CHARACTER is a friendly alias.
PERSON A real human (or AI) the show knows about — Jamie, Raja, audience walk-ups. The human.
ROSTER The lineup for a specific run — who is expected, who covers whom, who starts where.
cast The runtime fact "this person is currently playing this role." Swap mid-show.

Declaring a PERSON

PERSON jamie_lee
  display_name:    Jamie Lee
  pronouns:        they/them
  device:          jamie_phone_01
  content_tolerance: [no_strobe, no_loud_bells]
  accessibility:   [step_free]
  notes:           Veteran swing.

PERSONs live in the company's people/ folder and survive individual shows. Walk-up audience members get an ephemeral PERSON minted at the door. Every field except display_name is optional.

Declaring a ROSTER

ROSTER preview_night_05_28
  date:     2026-05-28T19:30
  capacity: 24

  cast
    Wren        := jamie_lee
    Bellkeeper  := raja_park
    Initiate    := any of [audience]      ← any walk-up
    Singer      := any of [pat_eberle, kim_ho, audience]

  swings
    Wren        := [raja_park, kim_ho]    ← priority order
    Bellkeeper  := [jamie_lee]

  locations
    BellTower   start with: [jamie_lee]

A ROSTER slot can be a named PERSON, a pool of acceptable PERSONs (any of [...]), or empty. The synthetic pool audience means "any walk-up." Empty slots are legal — the role plays as a "ghost" until you cast someone in. Load a roster at showtime with <load_roster: preview_night_05_28>.

Casting on the fly

<cast:    jamie_lee as Wren>            ← bind
<uncast:  Wren>                          ← release; role goes ghost
<recast:  Wren := kim_ho>                ← atomic swap; stats & goals survive
<promote: anonymous_walkup_12 as Initiate>
<demote:  kim_ho>                        ← stops playing; still in attendance

Recast is the deep one: when you swap Wren's player, the role's stats, knowledge, goals, and any in-flight scene keep running. Only the player changes.

Hooks and the as Participant alias

on participant joins
  <enroll: Participant → Initiates>
  -> orientation as Participant

The capitalised Participant means "the PERSON this event is about." The phrase as Participant at the end of a divert says "play orientation scoped to that one PERSON." Inside such a beat, self is the PERSON, and self.role is the ROLE they're currently bound to (or none if they're unbound audience). From a role-scoped beat, self.player is the PERSON playing the role.

Personal and character info, side by side

Both the simulator and the booth runtime have an inspection panel for every PERSON and every ROLE, addressed by the same dotted paths you write in expressions: 

jamie_lee.display_name              ← person face
jamie_lee.content_tolerance
jamie_lee.location
jamie_lee.role                      ← currently Wren

Wren.player                         ← role face: currently jamie_lee
Wren.stats.health
Wren.goals.find_keeper.state

The People panel lists PERSONs (with the role each is playing inline); the Roles panel lists ROLEs (with the player each is bound to inline). Pick whichever face the moment needs.

36. Cohorts and locations advanced

A cohort is a named group of participants. A location is a named place in your venue. Both are declared with the same shape as a character: 

COHORT Initiates
  label:    The Initiates
  capacity: 24

COHORT Singers
  label:    The Singers
  capacity: 8

LOCATION BellTower
  label:    The Bell Tower
  ambient:  bell-loop
  capacity: 8

LOCATION Nave
  label:    The Nave

Participants can be in one location at a time and any number of cohorts. The runtime emits ledger events as they move and join.

37. Broadcast scopes advanced

In a live show, different audience members can hear different things. <broadcast:> sends content only to the matching audience. 

<broadcast: participant(Participant)>
  NARRATOR
    (whispering)
    You hear it differently. You always have.

<broadcast: location(BellTower) but participant(Participant)>
  NARRATOR
    The others look up.

<broadcast: cohort(Singers) and location(BellTower)>
  <cue: private_choir>

The scope vocabulary:

AtomMeaning
participant(X)Just participant X.
cohort(C)Everyone in cohort C.
location(L)Everyone currently in location L.
A and BIntersection — in both A and B.
A but BDifference — in A, not in B.

38. Improv with pluggable advancement advanced

Sometimes you don't want to script every word — you want to give the performer a brief and let them improvise. Loom has a special parenthetical for that: 

BELLKEEPER
  (improv duration: 45s, advance on: any [pedal, speech(let us begin), gesture(Bow)])
  (Greet warmly. Find out why they came. Don't reveal the singing —
   that's act two.)

  -> next_beat

What's happening:

  • The first parenthetical (the one starting with improv) is the director's note — how long, and what makes the beat advance.
  • The second parenthetical is the performer's brief — what to play.
  • The runtime holds the playhead until any of the listed signals arrives, or the duration elapses.
Advance signalMeaning
pedalThe booth presses a pedal.
speech(phrase)A performer says the phrase (or the runtime hears it).
gesture(name)A motion-tracked gesture fires.
Quorum operatorMeaning
anyAdvance on the first signal.
allAdvance only when every signal has fired.
quorum(N)Advance when N have fired.

39. The booth — live patching advanced

In a live show, the booth (the operator's station) is just another client of the same runtime. The booth can:

  • Skip a participant past a beat.
  • Force-fire a cue.
  • Re-cast a role (swap one performer for another mid-show).
  • Retire a participant who left early.
  • Hot-reload a .loom patch without stopping the show.

Every booth action writes to the ledger, so the post-show audit shows exactly what was overridden, when, and by whom. This isn't a special mode of Loom — it's the same machinery the script uses, exposed in a different UI.

40. Generators — ambient life advanced

A generator is a long-running coroutine that yields content at intervals. Generators are how you build worlds that feel alive when nothing important is happening — dockworkers calling out, villagers gossiping, the wind picking up. 

GENERATOR HarborChorus
  tier:     ambient
  priority: 0.3

  loop
    wait random(20s, 60s)

    <if: Storm.active>
      DOCKHAND | FISHER
        (worried)
        <shuffle: Storm's close. | Sky's wrong. | Time to tie down.>

    <else if: Bell.ringing>
      VILLAGER
        (surprised)
        The bell! It's ringing!

    <else>
      FISHER | VILLAGER
        <cycle: Quiet night. | Stars are out. | Tide's calm.>

What's happening:

  • tier: ambient — runs on a slow budget (every ~2 seconds).
  • priority: 0.3 — relatively low priority; will be deferred if the scheduler is busy.
  • loop — runs forever (until cancelled).
  • wait random(20s, 60s) — pauses between 20 and 60 seconds.
  • Inside the loop, an if/else chain picks which line to play.

Generators can also live inside a character:

CHARACTER Elena
  generator daily_routine
    at 6am   go_to Home
    at 8am   go_to Bakery
    at noon  go_to Harbor

    every random(15m, 45m)
      <if: at Harbor and Weather.fog>
        yield bark from HarborFogChatter

A character with no generators is a static prop. A character with a few is a villager. A character with a dozen anchors a whole town.

41. Scenes — multi-step coroutines advanced

Where a generator yields ambient content, a SCENE drives a focused multi-step interaction. 

SCENE patrol(character)
  loop
    wait until character.spotted_intruder
    -> investigate as character

SCENE investigate(character)
  approach
    wait until character.at(Player.position)
    -> examine

  examine
    NPC
      (focused)
      Hmm. Something's not right.
    wait until character.deduction > 60
    -> confront

  confront
    return clue

What's new here:

  • Parameters — patrol(character) takes a character to attach to.
  • Labelled states — approach, examine, confront are inner state names you can jump between with ->.
  • wait until expression — block until the expression is true.
  • return value — produce a value and end the scene.

You launch a scene with either spawn (fire-and-forget) or run (await the return value):

<spawn: patrol with character: Guard1>            ← run in background

<let: outcome = run investigate(character: Wren)>  ← wait for return

42. Tiered scheduling advanced

When you have hundreds of characters and generators all alive at once, the runtime can't tick every one of them every frame. Loom uses three tiers, each with a per-tick budget:

TierTicks everyBest for
focalevery frame (~16ms)Active conversation, scenes the camera is in.
active~100msNearby NPCs, recently-spoken-with characters.
ambient~2 secondsDistant NPCs, world generators, background life.

You set a tier on a generator or scene with tier: focal, tier: active, or tier: ambient. If you don't set one, sensible defaults apply.

A scene marked tier: focal is never deferred — under load, the scheduler steals budget from ambient before dropping a focal frame.

43. Typed slots — filling holes at call sites advanced

"Typed slots" sound technical, but the idea is small: a beat, a character, or a scene can have holes that callers fill in. This is how you reuse one beat for many similar interactions.

On a character

CHARACTER Keeper
  voice: any
  home:  any of LOCATION

CHARACTER Wren is Keeper
  voice: female_alto
  home:  Lighthouse

Keeper has two unfilled slots (no defaults). It can't be instantiated on its own — it's an abstract template. Wren is Keeper fills the slots.

On a beat

== ask_about(topic, NPC)
  cast: NPC, Player

PLAYER
  Tell me about the {topic}.

<match: NPC.knows of topic>
  confirmed
    slot: answer            ← caller fills this
  unknown
    NPC
      I'm sorry. I don't know.

And at the call site:

-> ask_about with topic: bell, NPC: Wren
  answer:
    WREN
      The bell rings when the keeper is in danger.

The slot: answer in the beat says "the caller fills this with custom content." The caller's answer: block at the divert site is what slots in. The same beat handles asking Wren about the bell, asking Wren about the keepers, asking the fisher about the storm — same machinery, different answer.

44. A project is a folder intermediate

A Loom project is a folder. Anywhere in that folder, any file ending in .loom is part of the project. The runtime loads them all, resolves names across them, and starts at main.loom's entry beat. 

my-show/
├── main.loom                    ← the entry point
├── cast/
│   ├── Wren.loom                ← one character per file (optional)
│   ├── Player.loom
│   └── Bellkeeper.loom
├── locations/
│   ├── Lighthouse.loom
│   └── Harbor.loom
├── stats/
│   └── Combat.loom              ← shared stats profile
├── factions/
│   └── KeepersGuild.loom
├── beats/
│   ├── opening.loom
│   ├── ringing.loom             ← one beat per file
│   └── act_two/
│       ├── confrontation.loom
│       └── revelation.loom
└── generators/
    └── HarborChorus.loom        ← ambient life

The discipline:

  • main.loom is the entry. Its entry: property names the first beat.
  • Folders are for humans. Loom doesn't enforce a layout. Put files where you'd look for them.
  • Names are flat. A beat called ringing lives in beats/ringing.loom or main.loom or anywhere else — the resolver finds it.
  • Any declaration can live anywhere. Wren can be in cast/Wren.loom, or inline in main.loom. Your choice.

45. Diverts across files intermediate

Diverts cross file boundaries seamlessly. The playhead doesn't notice whether the next beat is in the same file or a different one.

FormMeaning
-> ringingJump to the beat ringing — wherever it lives.
-> Lighthouse/ringingDisambiguate by folder when two beats share a name.
-> WrenJump to the entry beat of the file declaring Wren.
-> cast/Wren#backstoryJump to a specific beat (backstory) inside cast/Wren.loom.
-> ask_about with topic: bell, NPC: WrenParameterised — fill slots at the call site.
-> (ask_about with topic: bell) ->Tunnel — jump, then return on <-.
-> ENDStop the playhead.
Two beats with the same name. If you accidentally create two beats called opening in different files, the resolver errors out by default — better than silently picking the wrong one. Qualify with the folder name to disambiguate (-> Lighthouse/opening).

<each visit> / first / then / finallyPick by visit count.
<after: COND> / <otherwise>Latching state morph.
<anchor: NAME>Name a position in the story.
<let: NAME = EXPR>Inline scope-local binding.

Core verbs (registered as functions you can call)

<sfx: NAME>Play a sound effect.
<cue: NAME>Fire a named cue (lighting, sound, anything subscribed).
<pause: DURATION>Wait DURATION.
<fire: EVENT>Fire a user-named event (consumed by on event … hooks).
<set: PATH OP VALUE>Mutate a value (see §16).
<spawn: SCENE>Launch a scene in the background.
<cancel: SCENE>Stop a running scene.
<goal: PATH ACTION>Force a goal — start, complete, reset.
<broadcast: SCOPE>Send the indented body only to the matching audience.
<enroll: PARTICIPANT → COHORT>Add a participant to a cohort.
<goto: WHO → WHERE>Move a character to a location.
<compose: EXPR>Compose / call a Luau expression.
<flash: COLOR, DURATION>(Example studio verb.) Flash the stage a colour.
<heal: WHO, AMOUNT>(Example studio verb.) Heal a character.
<shuffle: A | B | C>Random pick.
<cycle: A | B | C>Cycle through in order.
Studios add their own. The core directives are the ones every project gets for free. A particular studio (or even a particular show) can add directives that make sense for them — <moonlight>, <projector: video1>, <haptic: pulse>. The same registry, the same dispatch — the runtime doesn't care which.

51. Glossary beginner

action line
A flush-left paragraph describing what happens. Borrowed from screenplay.
anchor
A named position in the story. <anchor: NAME>. Used by since() and played() queries.
beat
A named scene. Declared with ==. The smallest unit the playhead can jump to.
booth
The live-show operator's station. Just another client of the same Loom runtime.
broadcast
A directive that sends content to a filtered subset of the audience.
character
A first-class entity with properties, knowledge, disposition, goals, and hooks. Declared with CHARACTER.
choice
A reader-driven branch. Starts with * (once-only) or + (sticky).
cohort
A named group of participants. Declared with COHORT.
directive
A runtime instruction in angle brackets. <sfx: bell>.
disposition
A character's feeling toward another character. trusts, respects, fears.
divert
A jump to another beat. -> ringing.
generator
A long-running coroutine that yields ambient content. Declared with GENERATOR or inside a character.
goal
A small state machine on a character with active / complete / fail predicates.
hook
An event-triggered piece of behaviour on a character. on meeting Player, on trust passes 60.
interpolation
Putting a value into text with {…}.
knot
Another word for "beat declaration." The == marker. Borrowed from Ink.
knowledge
What a character has learned. Declared inside knows:.
ledger
The story's permanent record. Every change writes to it. Queryable.
let
A reactive binding — a name for a live formula.
location
A named place in the world. Declared with LOCATION.
participant
A real audience member in a live show. First-class in the runtime.
parenthetical
A direction for the performer, in (parens).
playhead
The runtime's cursor through the story. Like a needle on a record.
project
A folder of .loom files rooted at main.loom.
reactive
Updates automatically when inputs change. lets and predicates are reactive.
scene
A multi-step coroutine with labelled inner states. Declared with SCENE.
scope (live)
The filter used by <broadcast:> — who hears this content.
slot (typed)
A hole in a beat / character / scene that the caller fills.
speaker cue
An ALL CAPS name on its own line indicating who speaks next.
sticky choice
A choice that doesn't disappear after being picked. Starts with +.
trait
A reusable behaviour bundle mixed into a character with is.
tunnel
A divert that returns. -> (x) -> goes; <- comes back.
weave
The branching graph traced by all possible playheads through the story.

52. Common errors and what they mean intermediate

UnterminatedBlockComment
You opened /* and never closed it with */. Find the opener and add a closer.
UnknownDivertTarget
You wrote -> foo but no beat named foo exists anywhere in the project. Check spelling, or qualify with a folder if two beats share the name.
AmbiguousDivertTarget
Two beats with the same name exist in different files. Qualify the divert: -> Lighthouse/opening.
RequiredSlotUnfilled
A character or trait has a required slot (no default) that nothing has filled. Either give it a default, or fill it in the child that instantiates the template.
UnknownDirective
You wrote <flash:> but no flash directive is registered. Check the verb name, or have the studio add it.
BadKnowledgeValue
You tried to <set: Wren.knows.bell_origin := maybe> but bell_origin only accepts unknown | suspects | confirmed. Use one of the declared values.
NoEntryBeat
Your main.loom has no entry: and no top-level ==. Add an entry beat.
Reading errors. Loom errors always point at a file and line. The editor surfaces them inline. When in doubt, the error message is more accurate than your memory — read the line it's pointing at carefully before changing anything else.

Where to go from here

You now know enough Loom to write a working story end-to-end — branching, with characters who have feelings and memory, optionally with live audience members and ambient world life.

The natural next steps:

  • Read the worked examples in packages/loom/examples/ — short, self-contained projects that demonstrate one feature each.
  • Skim the spec at docs/dev/loom-v3.html for the full surface, including features this guide skipped (factions, items, scene-coordinated multi-character scenes, multi-user authoring).
  • Look at the per-package CLAUDE.md files in packages/loom/ if you want to know how Loom is implemented under the hood.

And when you're stuck, the best move is usually to step away from the computer, sketch the scene as you'd act it out at a table read, and then come back and write only the lines you'd actually say. Loom is designed so the thing you write at the table is the thing the runtime runs.
