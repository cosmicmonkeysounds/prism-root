Loom editor — a live NLE for non-linear stories design

The Loom editor is a non-linear editor in the DAW / NLE sense: multitrack timeline, parallel clips, live cursors, inspectors, patcher overlays, and time travel. Stories that look like scripts get authored, rehearsed, and run in the same canvas that a video editor cuts a film in or a producer arranges a session in. The closest prior art is the pairing in Ableton Live — a Session view of clips that can fire at any time, and an Arrangement view of what actually happened — together with DaVinci Resolve's track-folder + inspector ergonomics and Max/MSP's patcher graph for causal inspection. v3 ships with a single linear Playhead that walks one beat at a time; that is enough to play a story but not enough to show one. A Loom show is a mesh of concurrent tracks — a Wren, a Bellkeeper, a chorus, an audience cohort, a director at the booth — each with its own state, its own history, its own current beat. The editor and the engine should both treat the show that way. This doc proposes the runtime + UI work to get there.

The four claims.
  1. One playhead is a lie. Every character is already advancing under its own volition (goals, generators, hooks); the runtime serialises that mesh into one stream so the v2 console UI can read it. The editor's mental model has to match the engine's actual shape: many tracks, one world.
  2. The story is a graph, not a transcript. The ledger is already a DAG — every event has a cause (a directive, a hook, a choice, a tick). Rendered as a transcript that structure dies. Rendered as a graph it becomes the primary surface for inspection, time-travel, and "why did this fire?" debugging.
  3. The editor is a window, not a player. Composing, directing, and running a show are three modes over the same canvas, not three apps. A writer dragging beats and a booth operator hot-patching a fainted performer are doing the same operation on the same graph.
  4. Volition is a track property. A track can be driven by the script (NPC), by a performer (scripted role with a human reading lines), or by an audience member (a participant). Switching modes mid-show is a binding change, not a different engine path.
  5. Two views, one timeline. Ableton Live's Session / Arrangement split is the right pairing. A Session view shows the grid of beats that could fire on each track, with global narrative branches as columns ("scenes") that fire across every track at once. An Arrangement view shows the same project as the linear multitrack record of what actually happened. Same store, same envelopes — two projections.

1. Why one playhead is wrong

v3 has more concurrency than the playhead lets you see. Right now:

  • Every ROLE with a generator is a coroutine running on the tiered scheduler (focal / active / ambient — spec §12.5). Wren's daily_routine and the HarborChorus are both ticking while the player is mid-dialogue with the Bellkeeper.
  • Every ROLE with goals is already a small state machine running independently (spec §10.3) — find_keeper pursues even when nothing in the focal beat references it.
  • Every PERSON has their own location and cohort state (spec v3 §13). A participant walking between rooms is a parallel movement timeline.
  • <spawn:> and <run:> exist precisely so beats can launch siblings (spec §12.3, §12.4). They are first-class.

The runtime threads all of that through one cursor — the Playhead — and surfaces it as a single Step stream. That's the right serialisation for the current TUI / web-editor preview, and it will stay the right one for "play this beat in isolation." But it is the wrong primary view for an authoring tool, because:

  1. Authoring questions are cross-track. "Where is Wren when the player is in the Nave?" "Which cohort hears this cue?" "Is anyone idle for more than 90 seconds in act one?" — none of these are answerable by reading the current beat's body.
  2. Debugging questions are causal. "Why did Wren just shift to hostile?" — that's a backward walk through the disposition mutation that crossed the threshold, the directive that issued it, the beat the directive was in, the divert that brought the playhead to that beat. The transcript shows you the result; the graph shows you the cause.
  3. Live-show questions are spatial. A booth operator's view is "twenty audience members across four rooms, plus six performers, plus a director cueing from a tablet" — not "what line is the playhead on." The current shell renders the wrong thing for the operator.

None of these need the playhead removed. They need a peer view of the same engine state organised by track, not by time.

2. The mesh model — Tracks, Mesh, shared World

Three new nouns. They subsume the playhead; they do not replace it (a single-track Mesh is a Playhead).

NounIsOwns
Track One independent cursor through the story. identity (what it is the cursor of — see below); frame stack; private dialogue history; subscription set of hook clauses; scheduler tier.
Mesh The set of currently live Tracks, plus their causal links. creation/retirement of tracks; cross-track hook routing; one shared Ledger; one shared World (Loro CRDT); the global scheduler.
Cell One unit of a Track's history — a beat-visit, an improv window, a generator yield, a directive call. span in real time; a pointer into the bundle (what was played); a snapshot id (what the world looked like after); the cause-edge that produced it.

A Track's identity is one of (spec v3 §13 vocabulary):

  • A ROLE. The track follows the fictional entity. Whoever plays the role (NPC, performer, walk-up) drives this track. Wren has a track.
  • A PERSON not bound to a role. Walk-up audience members get a track for themselves. Their location, cohort membership, content-tolerance, and any beat they're being broadcast into are on this track.
  • A COHORT. Group-scoped flow. The Initiates have a track; what they're collectively being addressed by sits on it.
  • An ambient GENERATOR. World-bound generators (the harbour chorus, the weather, the bell) each get their own track.
  • The director / booth. Operator actions (skip, recast, hot-patch) ride on a special "Booth" track that can route into any other.

Tracks all share one world (the Loro CRDT) and one ledger. They differ in what they're reading the world from: a Track's self-scope is its identity, so an expression like trust(Player) inside Wren's track resolves to Wren.trusts.Player; the same expression inside an Initiate's track resolves to Initiate.trusts.Player. Spec v3 §13.5 already had this rule for scoped beats; the Mesh generalises it.

A Track's private history is a slice of the ledger — every envelope whose subject is this track or whose cause-edge lands on it. Two participants in the same beat see overlapping but distinct slices: the broadcast envelope, the directives that fired on them, the dialogue they were addressed by.

3. The living graph — events as a DAG

Today's Ledger is a flat append-only vector of Event envelopes (spec implementation: §10.4, §13.4). Flat is fine for a transcript; insufficient for a graph. Every envelope grows two new fields: 

pub struct EnvelopeMeta {
    /// The track this envelope is "about" — the cursor whose cell
    /// produced or received it.
    pub track: TrackId,
    /// The cause edge: the prior envelope index that triggered this
    /// one. `None` for root events (player input, walk-up join,
    /// booth action, ambient generator tick).
    pub cause: Option,
}

Every existing path that pushes to the ledger now has to attach a cause. The wiring is mechanical:

EnvelopeCause
Action / Dialogue the beat-visit envelope that opened the current cell
Directive the body item index that fired it (carried through the playhead's instruction pointer)
WorldSet the directive that called <set:>
KnowledgeChanged the directive that wrote Character.knows.X
Hook firings (synthetic — see below) the envelope whose predicate they reacted to
CastBound / RolePromoted the directive or roster line that produced it
ParticipantJoined / walk-up events None — these are roots

The runtime currently fires hooks implicitly inside the playhead's yield-loop; we need to materialise the firing so the graph can show "this hook fired because that envelope landed." A new HookFired envelope captures it: 

HookFired {
    track:    TrackId,        // whose hook
    clause:   String,         // normalised event clause
    cause:    EnvelopeIdx,    // the envelope whose predicate triggered it
}

With that in place, the editor can render the ledger as a DAG: nodes are envelopes, edges are causes. A click on Wren's hostile tag walks back through HookFired → WorldSet → Directive → BeatVisit → Choice. The same DAG, projected onto track rows over time, is the multitrack timeline (next section).

4. The editor canvas — Session and Arrangement

The Ableton Live split is the right one. Session view is the grid of what could fire; Arrangement view is the linear record of what did. Both render the same Mesh; the toggle is one keystroke.

4.1 Session view — the clip grid

Rows are tracks. Columns are narrative scenes — the global story branches. A cell at (Wren, "Act II — the bell rings") is a clip: a launchable chunk of Loom (a beat, a scene, a generator phase, an improv window). Firing a column fires every clip in that column at once — the canonical "advance the show to Act II" gesture. Firing a single cell launches just that track's clip; follow actions on a clip (the Loom equivalent of a divert) auto-launch the next clip in the row when this one finishes.

Reading rules:

  • Columns are scenes (global branches). Firing a column fires every clip in it concurrently. Big narrative branches — Act II vs. Act II' — live as parallel scene sets, picked at runtime by an operator, a hook, or a choice. Small per-person branches (this audience member picked dialogue A; this one picked B) do not get their own columns; they're internal to a clip's content.
  • Track folders. Cohorts render as expandable folders ("Initiates ▽") whose children are the participant rows in the cohort. Collapsed, the folder shows the cohort's own flow; expanded, every participant row appears beneath it. Generators have an "Ambient" folder by default; the booth can pin specific generators above the fold during a show.
  • Clip vs. ongoing. A beat is a finite clip; a generator clip is ongoing and renders as a continuous audio-style waveform stripe (▓▓▓ / ░░░) rather than a discrete block. The runtime emits per-tier ticks the canvas paints into the stripe; zooming in expands the stripe into individual yields. This matches the DAW intuition of a live-recording track: it's running, it has level, you can scrub it.
  • Follow actions. A divert at the end of a clip is a follow action on the cell. The Session view shows it as a small arrow on the cell's right edge pointing at the next clip (often in the next column over). Re-targeting a follow action is a drag on that arrow — and the source-file divert updates to match.
  • The Booth folder pins to the top — its clips are operator-issued envelopes (<cast:>, <recast:>, <load_roster:>, hot-reloads, skips).

4.2 Arrangement view — the live record

Toggle to Arrangement. The same tracks become the rows of a linear timeline; the horizontal axis is real time during a show, beat-visit ordinal during composition. Each cell renders as a block whose width is its duration. Cause edges render as thin arcs from one cell to another — usually within a track (this beat's directive triggered the next), often across tracks (a directive in Wren's track fired a hook in the Bellkeeper's track).

Same track folders, same colour coding, same selection + inspector. In compose mode dragging a clip horizontally re-orders beats inside the source; in boot mode the same drag is a booth skip / re-cue. The Arrangement view is what a director hands a composer ("here's the cue list") and what the booth shows the stage manager during the run.

4.3 Patcher overlay — the causal graph

A third optional projection, modelled on Max/MSP: open the patcher window and the same envelopes appear as nodes with cause edges as cords. Useful when "what fired what" matters more than "when did it happen." Selecting an arc in Arrangement opens the patcher zoomed to that arc; selecting a node in the patcher scrolls Arrangement to that cell. Same data, three projections.

5. Three modes over one canvas

Same Mesh, same DAG, same canvas — three vocabularies on top.

ModeWhose toolVerbs the canvas exposes
Compose Writer / dramaturg edit beat bodies, drag-reorder beats inside a track, draw a divert by dragging from one beat to another, fork a beat into an <if> chain, declare a new ROLE / TRAIT / STATS, run a "dry play" that fakes audience joins.
Direct Director in rehearsal set the active ROSTER, dry-run the show with mocked participants, scrub backward to see how a beat lands under different disposition states, freeze a track while inspecting another, add notes to cells.
Boot (booth at showtime) Stage manager / booth operator cast, recast, promote, demote, skip, force-fire a cue, hot-reload a .loom patch, watch the ambient row for drift, route a microphone to a participant.

Mode is a UI affordance, not a runtime split. The engine doesn't know which mode the front-end is in; it just emits envelopes. The Compose mode talks to a Mesh whose clock is paused, Direct mode talks to a Mesh whose clock is mocked, Boot mode talks to a Mesh whose clock is real and whose participants are real. The same Loro store backs all three; collaboration "just works" because it is already in the substrate.

6. The inspector — picking a cell, picking an arc

Clicking a cell opens a side pane bound to that cell's state. Clicking a cause arc opens it bound to the envelope and its reverse-chain. The pane is the existing "panels" surface from spec v3 §13.11 — People / Roles / Roster / Stage — pinned to the selected cell.

What the pane shows for a beat-visit cell:

  • Header — track identity (ROLE name or PERSON name), beat name, visit count, real time span.
  • World snapshot — the world as it was after the cell completed. Snapshots are content-addressed (a hash of the affected world subtree) so cells that didn't mutate share storage with the previous snapshot.
  • Local state — for ROLE tracks: stats, knowledge, goal queue, hook subscription. For PERSON tracks: location, cohorts, content-tolerance, bound role. For COHORT tracks: membership.
  • Live expressions — a small REPL pinned to the cell's world. Wren.stats.health / jamie_lee.location work against the snapshot.
  • Causality — the cause chain (incoming arc), the effect chain (outgoing arcs). Each link clickable.

What it shows for a HookFired arc:

  • The hook source — the file/line that declared it.
  • The triggering envelope, fully expanded.
  • The hook's body lines as they ran, with directive results inline.
  • "Suppress this firing in replay" / "always fire from now on" — booth-mode override surfaces for debugging.

7. Time travel and branches

The ledger is append-only and content-addressed. Every cell carries a snapshot id; the world at any historical point is the snapshot the most recent cell pointed at. Rewinding is not a delete — it's a re-bind. Two scales of operation:

7.1 Global scrub and global branches

Most branches that matter to a story are global. The player ringing the bell or not ringing the bell affects every performer in every room — that's a global narrative branch. The Session view shows those branches as columns (§4.1); the Arrangement view shows them as a fork in the project's spine.

  • Global scrub. Drag the play-position cursor backward across the Arrangement. The world rebinds to the snapshot at that point; rendering replays each track up to its position at that time. The ledger past the scrub point becomes "future" — still in the store, just not enacted.
  • Global branch. From any cell, "branch from here" forks the project at that envelope. The Session view's column structure grows a new column for the branch; the Arrangement view shows the branches as parallel spines that can be diff-viewed against each other. Branch semantics map to Loro forks — both branches are first-class objects in the store, and the operator can merge one back in as a commit.
  • The story-level branch is the unit; not the per-track or per-person divergence.

7.2 Per-person branches do not get rails

Two audience members picking different dialogue with the same NPC is not a branch in this sense. It's local content variation inside a single broadcast scope: same beat, different body items chosen by <match:> or <if:> per-PERSON. The Arrangement view shows this as one cell whose inspector breaks down the per-person resolution — not as a forked timeline. Per-person variation is cheap (it's just expression evaluation against a participant scope); forking the project for every audience member would be unreadable.

The rule of thumb: if the operator at the booth would say "we're playing a different show now," it's a global branch. If they'd say "this person is hearing a slightly different cue," it isn't.

7.3 Rehearsal scrubs

In compose / direct mode, scrubbing is the rehearsal feature: "play that exchange again but with Wren's disposition still warm." The same global-scrub mechanism does it — the only thing different is that direct mode doesn't commit the replay back to the live ledger by default. The operator gets a "save this take" affordance if they want to keep it.

8. Volition — who is driving each track

Each Track has a driver — the source of its forward motion. v2 had two implicit drivers (script-driven for the focal beat, scheduler-driven for ambient generators). The Mesh formalises three:

DriverHow the track advancesExample
Scripted Walks the bundle's body items deterministically. Goals, generators, hooks all participate. An NPC patrol; an ambient generator; a focal beat with no live performer.
Performer Same body but waits on a human cue per dialogue line / per improv beat. The performer sees their lines on a prompter; the track advances when they press pedal / hit anchor phrase / complete the improv. An actor playing Wren reads scripted lines.
Participant Driven by the live PERSON's physical / device actions — location entries, taps, walk-up join, biometric cues. An audience member moving between rooms; a walk-up triggering a personalised beat by tapping a wristband.

A track's driver is mutable at runtime. A scripted Wren-track becomes performer-driven the moment <cast: jamie_lee as Wren> binds a PERSON. A performer who steps off becomes scripted again (or ghosts) without restarting the track. The canvas distinguishes drivers visually — a coloured stripe at the left of each track row, in the manner of Resolve's track-type badges.

9. Runtime changes — Playhead → PlayMesh

Concrete shape of the work in loom-runtime:

9.1 New types

pub struct TrackId(pub u32);

pub enum TrackIdentity {
    Role(String),
    Person(String),
    Cohort(String),
    AmbientGenerator(String),
    Booth,
}

pub enum Driver {
    Scripted,
    Performer { device: Option<String> },
    Participant { person: String },
}

pub struct Track {
    pub id: TrackId,
    pub identity: TrackIdentity,
    pub driver: Driver,
    pub tier: Tier,                        // scheduler tier
    pub stack: Vec<Frame>,                 // existing Frame, scoped to this track
    pub local_world_overlay: WorldOverlay, // self.* + local lets (spec §9.6.2)
    pub history: Vec<EnvelopeIdx>,         // private slice of the ledger
    pub subscriptions: Vec<HookSubscription>,
}

pub struct PlayMesh {
    pub bundle: Arc<Bundle>,
    pub world: World,                      // shared Loro store
    pub ledger: Ledger,                    // shared, now with EnvelopeMeta
    pub scheduler: Scheduler,
    pub tracks: SlotMap<TrackId, Track>,
    pub focus: Option<TrackId>,            // booth/editor "PoV"
    pub clock: Clock,                      // real | mocked | paused
}

9.2 Step model

PlayMesh::step() runs one scheduler tick across every track and returns a vector of (TrackId, Step) pairs. The existing Step enum is reused per-track: 

impl PlayMesh {
    pub fn step(&mut self) -> Vec<(TrackId, Step)> { … }

    /// Run a single track in isolation — the existing Playhead API
    /// reborn as a slice of the Mesh.
    pub fn step_one(&mut self, id: TrackId) -> Result<Step, PlayError> { … }

    /// Drive the Mesh until every track is idle or waiting on input.
    pub fn run_to_quiescence(&mut self) { … }

    /// `Playhead` becomes a thin wrapper: a Mesh with one Scripted
    /// track. Existing callers keep working.
    pub fn into_playhead(self) -> Playhead { … }
}

9.3 Hook routing

Hooks were already declared per-ROLE / per-TRAIT and the runtime fires them on matching ledger events. With the Mesh the rule becomes: a hook declared inside a ROLE fires on the track that binds that role; a top-level hook (on participant joins) spawns a new Participant track or routes to the relevant one. HookFired envelopes carry the track id so the graph can render the arc.

9.4 Cell synthesis

Cells are not an extra storage layer — they're a view over the ledger keyed by (track, span). The runtime emits two new envelopes per beat-visit so the cell boundaries are explicit: CellEntered { track, cell_kind, bundle_ref } and CellExited { track, snapshot }. The editor's multitrack canvas reads cell rows by paging through the ledger and grouping by track id between Entered/Exited pairs.

9.5 Snapshots

After every CellExited the runtime hashes the world subtrees the track touched and writes a Snapshot { id, base, diff } record. Snapshots chain — each one is a diff against the previous on the same track plus diffs against concurrent changes from other tracks. Scrubbing back to a cell rebinds the world to the snapshot id; the Loro store can do this without a full materialisation by replaying ops.

10. Editor architecture — components and panels

The editor is the React/Vite/CodeMirror app under packages/loom/editor. New surfaces:

ComponentRole
<MeshCanvas /> The multitrack timeline. Reads PlayMesh::tracks + the cell-paginated ledger; renders rows, cells, cause arcs. Handles pan / zoom / drag-to-divert.
<TrackRow /> One row, one track. Carries the driver badge, the role/person portrait, and the cell strip.
<CellInspector /> The side pane (§6). Bound to a selected cell or arc.
<GraphOverlay /> Toggleable second canvas — same ledger, rendered as a classical DAG. Useful when "what fired what" matters more than "when did it fire."
<CompositionPalette /> Compose-mode toolbar. New ROLE / new beat / new TRAIT / stub generator. Drag from palette onto canvas creates and inserts.
<BoothPanel /> Boot-mode actions: cast, recast, promote, skip, hot-reload, route mic, force-fire cue. Every action is a directive call so the ledger captures the operator's intent.
<ScriptEditor /> CodeMirror, still the source-of-truth view. Bidirectional — writing in the source updates the canvas; dragging a beat on the canvas re-emits its declaration in the source.

Data flow: loom-server hosts the PlayMesh; the editor subscribes to the ledger over WS, pages cells lazily by (track, time-range), and applies operator actions as directive calls. Compose-mode edits are Loro ops on the source files. Booth-mode edits are directive calls on the running Mesh.

11. Migration from the single playhead

Two-phase, non-breaking.

11.1 Phase A — Mesh as a wrapper

Land PlayMesh with exactly one scripted track that delegates to the current Playhead. Add the EnvelopeMeta { track, cause } fields to every existing ledger push site (TrackId is always 0; cause is always the previous envelope on the same track). Emit CellEntered / CellExited around each beat-visit. No editor changes yet; the existing TUI / web preview keeps reading the same Step stream.

This phase is mostly mechanical wiring and a new envelope. It unblocks the canvas without changing semantics.

11.2 Phase B — multiple drivers

Introduce the four Driver variants. Spawn a Track per ROLE that has goals or character-bound generators (today they ride the scheduler invisibly — this just gives them their own row). Spawn a Track per live PERSON. Spawn the Booth track. Route hooks through track ids.

This is the visible phase: the canvas suddenly has many rows; the inspector becomes useful; per-track rewind unlocks.

12. Resolved design decisions

Decisions captured here are deliberate; they constrain the implementation. Anything not on this list is fair game in the build-out.

12.1 Branches are global, not per-track

The story branches that get a column / a fork / a rail are the ones the operator at the booth would describe as "we're playing a different show now" — the bell rings vs. doesn't ring; the Bellkeeper lives vs. dies; act II vs. act II' (§7.1). Per-person variation (two audience members picking different dialogue with the same NPC) stays inside a single cell as <match:> / <if:> resolution in a participant scope — it does not grow its own rail. This is the same rule Ableton applies to Session view: scenes are the global-fire unit, clip parameters are the per-instance variation.

12.2 Generators render as ongoing recording-style cells

A generator on a track does not produce N tiny discrete cells. It produces one ongoing cell that renders the way an audio track records in a DAW — a continuous stripe whose level / colour reflects activity (current yield, current state, scheduler tier load). Per-yield envelopes are still in the ledger; the canvas paints them into the stripe and exposes them on zoom-in. Pausing, scrubbing, and slicing a generator cell behave like cutting a live audio take in Resolve — the engine emits a synthetic boundary envelope and starts a new ongoing cell at the cut.

12.3 Cohorts are track folders, not their own tracks

A cohort is a targeting mask, not an actor. It renders as an expandable folder in the track header, the way Resolve and Ableton group tracks: collapsed shows aggregate activity for the cohort, expanded reveals every PERSON / ROLE bound to it as its own child row. A broadcast addressed to the cohort highlights the folder header and (in expanded view) the receiving children. The folder also functions as a track-routing point: a directive issued to Initiates routes to each child row's history.

12.4 Drag grammar on the canvas

Modelled on the consistent verbs of Live + Resolve + Max:

GestureSession viewArrangement viewPatcher overlay

▶ a cell fire one clip on its track — —
▶▶ a column fire every clip in the scene — —

Every gesture lowers to a small set of operations on the bundle (compose mode) or the running Mesh (boot mode); the source-file view stays the canonical representation.

12.5 Fan-in causes

Goal predicates that re-evaluate on every dependency can be triggered by multiple envelopes at once. The cause field on an envelope is a singleton; multi-cause firings emit one HookFired per triggering envelope, all pointing at the same hook clause. The patcher overlay then renders a natural fan-in (multiple cords into one node), the way Max renders concurrent inputs to an object. No special data shape; the rendering does the work.

12.6 Live + composition share one Loro store

Compose-mode edits land as Loro ops on the source files; boot-mode actions land as Loro ops on the running ledger; rehearsal rewinds branch the ledger temporarily and commit on the operator's "save take" gesture. Collaboration "just works" because Loro already handles concurrent edits; the editor just exposes the branch / commit gestures plainly. The pattern mirrors Resolve's Project Library — many cuts off one media pool — and Max's patcher-with-presentation duality.

13. Still open

  • Clip authoring directly on Session. Dragging cells into empty grid slots to create new beats is intuitive, but the round-trip into source-file structure (file path, declaration order, mixin clauses) needs a clear convention. Prototype before locking.
  • Aggregate clocks across branches. When two global branches both originate from a single cell, their sibling clocks need a deterministic ordering for ledger reads that span them. Lean on Loro's hybrid clock; UI surfaces this as a branch picker in the time bar.
  • Booth-side undo discipline. An accidental recast at showtime should be reversible — but only in a way the ledger captures (a corrective envelope) rather than a destructive undo. The undo affordance is therefore "issue the inverse directive" not "rewrite history."
